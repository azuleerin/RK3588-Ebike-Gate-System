# 4 路解除限帧全链路 —— 稳态吞吐权威测量

> **日期**: 2026-11-20  **板子**: RK3588 (3 核 NPU / 8 核 CPU)
> **被测程序**: 生产二进制 `rk_gate` (黑盒驱动, **未修改主工程任何代码**)
> **模型**: `ebike_int8_rk2332.rknn` (YOLOv8n INT8 640×640) + `ppocrv4_rec_fp16.rknn` (PP-OCRv4 rec)
> **测量条件**: 板子独占 · NPU 无第二租户 · 频率锁死 1000 MHz (`min_freq = max_freq`)

---

## 1. 权威数字

| 项 | 值 |
|---|---|
| **4 路解除限帧全链路稳态吞吐 (中位数)** | **87.42 FPS** |
| 同上, P95 (10 秒滑窗吞吐序列) | **95.0 FPS** |
| 三轮实测值 | 88.55 / 87.42 / 87.42 FPS (轮间极差 **1.29%**) |
| 每路交付 FPS (稳态窗口均值) | ch1 **19.0** · ch2 **24.1** · ch3 **22.6** · ch4 **22.0** |

**口径**: 稳态窗口 `[30s, 180s]`, 用**帧计数器差**算吞吐
(`(frames_end − frames_start) / (t_end − t_start)`), 不用 `rk_gate` 自报的
`deliv` —— 那是**从开跑起算的累计平均**, 会被启动瞬态抬高。

---

## 2. 一句话结论

> **最终 FPS = 87.42 FPS (中位数)。瓶颈在【检测排队】, 不在识别排队。**
>
> 每核 NPU 占用已到 **93%** (检测 81~82% + 识别 11%), NPU 算力饱和;
> `detwait` 37.2 ms − `npu` 27.7 ms = **9.5 ms 的排队, 4 路全有**。
> 识别等待 (`ocrwait`) 只出现在近景两路 (ch1/ch3), ch2/ch4 = **0** —— 识别
> 只占了每核 11% 的算力, 是"搭车"而不是瓶颈。

## 3. 测量条件与命令

```bash
# 预检 1: 板子安静 (必须为空)
ps -eo pid,args | grep -E "npu_layer_bench|model_perf_bench|batch_infer_bench|prune_finetune|export_quantize" | grep -v grep

# 预检 2: 先让看门狗闭嘴, 再停服务 (顺序不能反)
sudo touch /run/rk-gate/paused
sudo systemctl stop rk-gate rk-pipeline rk-night-soak-monitor

# 预检 3: 锁频 (target_freq 是只读的, 必须改 min + max)
sudo sh -c \
  'echo 1000000000 > /sys/class/devfreq/fdab0000.npu/min_freq; \
   echo 1000000000 > /sys/class/devfreq/fdab0000.npu/max_freq'

# 被测命令 (只改命令行参数, 不改代码)
rk_gate --model models/ebike_int8_rk2332.rknn \
        --ppocr models/ppocrv4_rec_fp16.rknn \
        --det-core 0,1,2 --ocr-core 0,1,2 --det-workers 3 --ocr-workers 3 \
        --max-fps 0 --stats-interval 20 --duration 180 \
        --ch ch1:...:near --ch ch2:...:high --ch ch3:...:near --ch ch4:...:high
```

**与生产配置的差异**: 只有 `--max-fps 20` → `0` (解除限帧) 和 `--stats-interval 100` → `20`
(日志密度, 每秒多 5 行, 对吞吐无影响)。核绑定 / worker 数 / ROI / IPM / 模型全部与生产一致。

| 轮次 | 帧数区间 | 窗口秒 | 稳态 FPS | 每帧 npu= | 三核 debugfs (均值) | DDR dmc | 整机 CPU | 频率 |

**分段吞吐 (三轮形状一致 —— 是视频内容驱动的, 不是随机噪声)**:

| 窗口 | 轮1 | 轮2 | 轮3 |
|---|---|---|---|
| 0~30 s | 91.8 | 92.5 | 91.1 |
| 30~60 s | 85.4 | 85.4 | 85.4 |

> 吞吐在 **82 ~ 93 FPS** 之间摆动, 三轮形状几乎重合。根因是**内容**:
> 近景两路 (ch1/ch3) 在某些时段检出更多车牌 → 识别任务涌入 → 每核 NPU 更满 →
> 检测速率被压低; 车牌少了又回升。**这是业务负载的真实特征, 不是测量噪声。**

## 6. 瓶颈定位

### 每核 NPU 占用 (`rk_gate` 收尾自报, 应用内口径 = 该核 rknn_run 耗时 / 墙钟)

| 核 | 检测 | 识别 | 合计 |
|---|---|---|---|
| Core0 | 81.3% | 11.3% | **92.6%** |
| Core1 | 82.0% | 11.8% | **93.8%** |
| Core2 | 82.1% | 11.3% | **93.4%** |

三核**均衡**在 93% 附近 —— 没有单核短板, 是**整体算力饱和**。

### 排队在哪

| 路径 | 现象 | 出现在哪些路 |
|---|---|---|
| **检测** | `detwait` 37.2 ms − `npu` 27.7 ms = **9.5 ms 排队** | **全部 4 路** |
| **识别** | `ocrwait` 近景两路 40~55 ms; 高位两路 **0.00 ms** | 只有 ch1 / ch3 |

→ **瓶颈在检测排队。** 根因是每核 NPU 已 93% 满, 而检测占了其中的 82%;
识别只占 11%, 是搭车。

### 不是瓶颈的东西

| 环节 | 实测 | 判断 |
|---|---|---|
| 整机 CPU | 13.1% (8 核口径, 折合 1.05 核) | 远未饱和 |
| DDR 带宽 (dmc) | 34.1% | 远未饱和 |
| RGA 预处理 | 2.1~7.1 ms/帧 (4 路合计约 20 ms/s) | 占比 < 2% |
| 源码帧率上限 | 4 路合计 171.5 FPS | 远高于 87.4 |

## 8. 诚实边界

- **87.42 FPS 是"带文件源回放"的端到端交付吞吐**, 含视频内容驱动的起伏
  (82~93 FPS)。若只取最好的 10 秒窗口, 数字是 95~98 FPS。
  **给老板汇报用 87.42 FPS 这个中位数**, 因为它是可复现的;
  别用 P95 去做承诺。
- **"你无上下文的核"这条判据在本场景不适用** —— 4 路全链路把 3 颗核都用上了,
  没有"空闲核"可查。因此改用 **C3 回落证明** + **C4 `npu=` 干净带** + **C1 进程判据**
  三者联合, 效果等价(甚至更严): 若有第二租户, `npu=` 必然被抬高。
- **每轮 180s, 4 路视频源循环播放**。源本身够长 (445~1404s), 180s 内不回卷,
  所以没有"回卷重缓冲"混入。
- 本次只测吞吐, 不涉及长跑稳定性 / 内存平线 (那是 `SOAK_REPORT_20261118.md` 的范围)。
