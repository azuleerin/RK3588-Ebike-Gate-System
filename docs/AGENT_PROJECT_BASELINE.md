# 项目背景与约束（双 Agent 通用只读）

> **适用范围**：RK3588 边缘 AI 大门感知系统（小区/城中村 4 路并发场景）交付收尾与开源发版阶段。
> **文件性质**：**只读基线**。本文件描述项目背景、环境事实、目录权限、实测坑位、交付标准与行为规范，

## 一、一句话项目背景

本项目基于 RK3588 边缘计算平台，面向小区/城中村大门场景，实现 4 路并发（2 路近景 PP-OCR 识别 + 2 路高位 YOLO 检测测速）的实时车牌识别与测速系统，当前处于交付收尾与开源发版阶段。

---

## 二、环境事实（规划与执行时默认成立）

- **硬件平台**：Rockchip RK3588 (reComputer 开发套件)，8 核 CPU (4×A76 + 4×A55)，8GB 内存，3 核 NPU (算力 6 TOPS，支持独立调度)。
- **系统内核**：Armbian Linux（Ubuntu stable），内核版本 6.1.172-vendor-seeed-rk3588，架构 aarch64。
- **核心推理栈**：RKNN Toolkit2 `v2.3.2`（模型编译与板端 `librknnrt.so` 严格对齐）。生产环境模型为 `YOLOv8` (INT8) 与 `PP-OCRv4` (FP16，含汉字省份字典)。
- **硬件加速栈**：MPP 硬解 `1.5.0-1`，RGA 驱动 `1.3.13`，必须强制走 DMA-BUF 零拷贝。
- **编程语言与编译**：C++17 为核心流水线，Python 3 为辅助脚本；CMake + GCC 15.2.0 板端原生编译。
- **已验证能力**：单板 4 路并发稳定，实现 9.44 小时无崩溃长跑，内存活堆净增 +31KB（绝对平线）；Web 控制台 3.0 支持真实硬件单元开关联动与断线自动重连。

## 四、实测坑位库（全部验证过，规划必须规避）

### 【坑位 01】RKNN 版本不匹配导致模型加载失败

- **现象**：模型载入报错，或推理结果全零。
- **根因**：RKNN Toolkit 版本高于板端 `librknnrt.so` 版本。
- **解法**：强制使用 `v2.3.2` Toolkit 编译，用 `rknn_query` 校验版本哈希一致。

### 【坑位 02】长跑内存微涨（活堆漏液）

- **现象**：长时间运行后 RSS 缓慢上升。
- **根因**：`rknn_outputs_get` 每次推理未预分配缓冲，且 `AVFrame` 结构体未 `free`（只 unref）。
- **解法**：使用 `is_prealloc=1` 预分配输出，用 `av_frame_free()` 替代 `av_frame_unref()`，定期调用 `malloc_trim(0)`。

### 【坑位 03】多线程下段错误/死锁（悬垂指针）

- **现象**：LPR 裁剪阶段偶发段错误，甚至引发内核 panic。
- **根因**：MPP 解码输出的 `MppFrame` 在流水线中被过早 `deinit`，导致悬垂 fd。
- **解法**：引入 RAII 机制（`MppFrameGuard`），将其所有权托管到本帧生命周期结束。

### 【坑位 04】RGA 预处理导致内存越界/图像撕裂

- **现象**：RGA 报错或输出花屏，严重时系统崩溃。
- **根因**：`rga_buffer_t` 的 `wstride` 参数单位是**像素**，误传成了字节（乘了 3）。
- **解法**：确保 `wstride` 传像素值，且目标宽度必须按 16 字节对齐。

### 【坑位 05】车牌识别乱码/置信度低

- **现象**：PP-OCR 输出 `ANT` 等乱码。
- **根因**：为了省算力从 640 检测小图上裁剪 ROI，导致像素严重丢失。
- **解法**：必须取 YOLO 的框坐标，回到 **1080P 原图**上裁切，再送给 OCR。

### 【坑位 06】视频流输入积压崩溃

- **现象**：读取本地文件瞬间崩溃或假死。
- **根因**：文件读取速度极快，瞬间灌爆 MPP 输入队列。
- **解法**：必须引入背压机制，按源帧率限速（Pacing），或抽帧推理。

### 【坑位 07】小车牌识别不出“苏”等汉字

- **现象**：省份简称被丢弃，或识别成字母。
- **根因**：模型字典字符集不含汉字，或输入的图片是白字绿底（模型训练域是黑字白底）。
- **解法**：换用支持 6625 类汉字的 PP-OCRv4 FP16 模型，强制开启灰度反白处理。

## 五、交付标准与统一口径

### 1. 文档规范

- **README.md**：必须包含徽章、项目简介、核心亮点、性能指标、A/B 对比图、流水线图、目录结构、一键启动命令、Release 链接。
- **PDF 白皮书**：必须包含架构设计、硬件加速实测、崩溃排雷记录、现场适配指南。

### 2. 代码与提交规范

- 每次 `commit` 必须包含清晰的 message，格式：`feat/fix/docs(模块): 简短描述`。
- `.gitignore` 必须排除：`*.mp4` (大视频)、`build*/` (编译中间件)、`*.rknn` (大模型，需单独处理或放 Release)、`.venv`。

### 3. 数据口径与验证标准

- **数据真源**：所有性能指标（FPS、CPU、NPU 占用）必须来自板端真实运行的 `debugfs` 或 `top` 采样。
- **测试条件**：性能对比必须保持单变量原则（如同跑 600 帧、同开 PP-OCR，仅关硬解）。
- **禁止行为**：严禁在汇报材料和文档中写“预计、大概、估算”的虚假数据。

### 4. 发版规范

- **Release 命名**：`vX.Y-功能简述`（如 `v2.0-gate-4ch`）。
- **必带附件**：发版时必须附带自动生成的《RK3588边缘AI系统交付白皮书.pdf》。

## 六、Agent 行为规范与交互规则

### 1. 输出风格

- **结构**：结论先行，先给最终判断或结果，再逐步拆解原因。
- **排版**：多用表格、列表、加粗关键字，禁止说废话和寒暄客套。

### 2. 执行规则

- **报错处理**：必须按 `现象 -> 根因 -> 修复步骤 -> 验证方法` 四步走，禁止瞎猜。
- **交付命令**：给出的 Shell/Bash 命令必须是"可直接复制粘贴执行"的完整版，禁止用 `<替换项>` 占位而不说明替换逻辑。
- **环境变更**：修改网段、切代理、锁频等操作，必须显式告知对环境的副作用。

### 3. 质量底线

- 代码交付前，必须通过本地 `make -j8` 编译零警告，且通过 300 帧冒烟测试。
- 如果遇到不确定的硬件行为，必须如实标明风险，禁止强行跑测试。

### 4. 绝对禁止项

- 禁止在未打 Tag 或未提交当前 Git 树的情况下，开启新的宏大重构。
- 禁止私自删除 `archive/` 和 `models/` 目录下的任何文件。

## 七、安全红线

1. **绝对不能上传/喂给模型的数据**：包含内部网络 IP 拓扑、公司敏感数据的原始码流、私有的 Personal Access Token (PAT)。
2. **必须人工操作的场景**：涉及板子**断电重启、物理插拔网线/摄像头、重置路由器、操作 GitHub 账户生成 Token** 等物理与账号高危操作。
3. **禁止 Agent 执行的操作**：
   - 禁止 `rm -rf /` 或删除 `.git` 仓库。
   - 禁止强制覆写已被标记为稳定的旧代码（如 `main.cc` 单路逻辑），必须新建文件或加宏开关。
   - 禁止在未经允许的情况下修改 `models/` 目录下的生产模型。
