# thread_bench —— RK3588 三核 NPU 极限并发测试台

> 一个**完全独立**的测试台: 不接入主工程 `rk3588_zero_copy`, 不共用它的任何 `.cc/.h`,
> 不改它的 CMakeLists。它只依赖板上的 `librknnrt.so` + `rknn_api.h`,
> 目的是在**隔离环境**里单独回答三个问题:
>
> 1. 多路并发下, **最佳的工作线程数 T** 是多少?
> 2. **核该怎么绑**?(AUTO / 均匀分核 / 三核全开共享)
> 3. **T > 3 到底会不会把 CPU 抢占 / DDR 带宽打爆?**
>
> 硬件: Rockchip RK3588(3 核 NPU, 6 TOPS; 8 核 CPU = 4×A76 + 4×A55)
> 运行时: RKNN Toolkit2 **v2.3.2**(`/usr/lib/librknnrt.so`), 模型 `ebike_int8_rk2332.rknn`

---

## 一、5 分钟上手

```bash
cd thread_bench
cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j8

# 单组: 4 路 x 25fps, 6 个工作线程, 均匀分核
./build/thread_bench --model ../models/ebike_int8_rk2332.rknn \
    --threads 6 --strategy round --duration 30 --warmup 5

# 全矩阵(4 个阶段, 出 Markdown)
./scripts/run_bench.sh --duration 25 --model2 ../models/ppocrv4_rec_int8.rknn --phase all
#   -> results/<时间戳>/*.jsonl  +  bench_<时间戳>.md
```

> 板子上 `/sys/kernel/debug/rknpu/load` 对普通用户是 **Permission denied**,
> 所以 NPU 核占用率用**应用侧口径**(见 §三)算, 它不需要 root。
> 想额外拿到驱动侧的 load: `./scripts/run_bench.sh --use-sudo`。

### 线程模型

```
                 ┌──────────────── 主线程 = Producer ────────────────┐
                 │  按 --fps 错相推 4 路帧 (或 unlimited 死循环狂推)  │
                 │  push() 永不阻塞: 队列满 -> 丢最旧 -> 计数          │
                 └───────────────────────┬──────────────────────────┘
                                         │ 定长环形队列 (默认 64)
                     ┌───────────────────┼───────────────────┐
                     ▼                   ▼                   ▼
              ┌────────────┐      ┌────────────┐      ┌────────────┐
              │ worker 0   │      │ worker 1   │ ...  │ worker T-1 │
              │ ctx1(+ctx2)│      │ ctx1(+ctx2)│      │ ctx1(+ctx2)│
              │ rknn_run   │      │ rknn_run   │      │ rknn_run   │
              └────────────┘      └────────────┘      └────────────┘

  资源监控线程: 每 1 秒采一次 CPU / RSS / 堆 / NPU load, 打到 stderr
  stdout: 每组配置一行 JSON, 供脚本汇总
```

### 核心类

| 类 | 职责 | 关键点 |
|---|---|---|
| `FrameQueue` | 公共帧队列 | **定长环形**, 不用 `std::deque`(libstdc++ 的 `deque` 在 `pop_front` 时会释放内存块 = 热循环里的 `free`); 满了丢最旧, 生产者零阻塞 |
| `NpuWorker` | 一个工作线程 | 在**自己线程内** `rknn_init` / `rknn_run` / `rknn_destroy`; 每 worker 一(或两)个上下文 + 各自的零拷贝输入缓冲 + 预分配输出缓冲 |
| `LatencyRecorder` | 三序列延迟采样 | 启动时一次性分配, 热循环里 `atomic fetch_add` 抢唯一索引写入, **无锁无分配**; 分位数在窗口结束后排序 |
| `SysProbe` | 资源采样 | `/proc` 全部走 `open`+`pread`+栈缓冲, 采样时零堆分配 |

## 三、指标口径(和主工程对齐, 别混用)

| 指标 | 定义 | 为什么这么定 |
|---|---|---|
| **吞吐 FPS** | 成功推理帧数 ÷ 测量窗口(墙钟) | 并行下"各阶段耗时相加"没有意义, 吞吐只能用墙钟算 |
| **e2e 延迟** | 生产者入队 → 结果就绪 | 业务口径, **含排队等待** |
| **M1 / M2 延迟** | `rknn_run` + `outputs_get` | 这才是**真正占着 NPU 核**的时间 |
| **排队时间** | e2e − M1 | NPU 前面排了多少队 |
| **核占用 %** | Σ(该核 worker 的驱动实测推理耗时) ÷ (该核 worker 数 × 窗口) | ★ 见下方"为什么要归一化" |
| **NPU 算力 %** | Σ(所有 worker 的驱动实测推理耗时) ÷ 窗口 | 三核满载 = 300% |
| **CPU %** | `/proc/self/stat` 的 utime+stime ÷ 窗口 ÷ 8 核 | 整机口径 |
| **堆斜率 KB/min** | `mallinfo2().uordblks` 在窗口内的变化率 | **内存平线的直接证据**(负值 = 在缩, 不是在涨) |

> 双模型时, 一个 worker 的两个上下文在**同一颗核上是串行**的,
> 所以每核占用要把两个模型的耗时**先加总再归一化**(`core_total_pct`),
> 否则会低估一半。JSON 里 `core_m1_pct` / `core_m2_pct` 是按模型拆开的明细。

### ★ 为什么核占用要按"该核 worker 数"归一化

同一颗核上挂 N 个上下文时, 它们**串行**跑。驱动给每次推理报的 `run_duration`
含"等前面那个上下文让出核"的时间, 于是把 N 个 worker 的时长加起来 = N × 窗口(核饱和时)。
直接除以窗口会得到 `N00%`, 看起来像超载 —— 其实那正是"核被抢"的表现, 不是利用率。

所以: **核占用 = Σ时长 ÷ (该核 worker 数 × 窗口)**, 上限 100%。
原始的和另外报在 `core_m1_sum_pct` 里, 一个数都不藏。

> 口径说明: `rknn_query(RKNN_QUERY_PERF_RUN)` 报的是驱动侧的推理耗时,
> 不含"提交到进核之前"的排队, 但**含**同核其他上下文占核期间的等待。
> 想要纯粹的"硬件算了几毫秒", 板子上读不到 debugfs 时只能用这个近似值。

## 四、四条红线怎么落地的

| 红线 | 落地方式 | 怎么验证 |
|---|---|---|
| **零拷贝** | `rknn_create_mem` 让运行时分配一块 NPU 可直读的物理内存, `rknn_set_io_mem` 绑到输入张量。合成图案**只在启动时写一次**, 热循环里对输入缓冲的写次数 = **0** | 代码里热循环只有 `rknn_run` / `rknn_outputs_get` / `rknn_outputs_release` 三个 runtime 调用, 没有 memcpy |
| **内存平线** | 启动时一次性分配: 输入 mem、**预分配输出缓冲**、延迟采样数组、队列数组、模型字节。测量窗口内**零 malloc/free** | `mallinfo2().uordblks` 斜率 + `VmRSS`/`VmHWM` 实测 |
| **纯 C++ 多线程** | 只用 `std::thread` / `std::mutex` / `std::condition_variable` / 原子变量, 零第三方依赖 | `include/` 下只有 5 个头文件 |
| **丢帧防雪崩** | 队列满 → 丢**最旧**的一帧并计数, **生产者永不阻塞** | `--producer-mode unlimited` 专门压这条路径 |

### 与主工程的两处**故意**不同

1. **输出缓冲用 `is_prealloc = 1`**(主工程 `npu_pool.cc:356` 用的是 `is_prealloc = 0`)。
   `is_prealloc = 0` 意味着**每帧**由 runtime 去 malloc 一块输出缓冲 —— 那会直接破坏"内存平线"。
   本测试台启动时分配一次, 每帧直接写进去。
2. **`want_float = 0`**(主工程用 `1`)。保持模型原生量化格式, 避免驱动额外做一次 float 转换
   (那也要分配)。本测试台不解读输出, 不需要 float。

### ★ RKNN 上下文不能跨线程(踩过的坑)

> 在 A 线程 `rknn_init`, 拿 B 线程 `rknn_run`, 运行时内部**死锁** ——
> 表现是所有线程全卡在 futex, 一帧都不动(主工程 `npu_pool.cc:269` 的注释)。

所以本测试台把这件事做成**结构性的**: `NpuWorker::loop()` 是唯一接触 `ctx` 的地方,
而它就是那个 worker 线程本身。上下文在**本线程**创建, 在**本线程**销毁。

### 6.5 资源占用(所有配置的汇总)

| 指标 | 真实负载 | 饱和负载 | 说明 |
|---|---|---|---|
| CPU 占用 | 1.6% ~ 2.1% | 2.0% ~ 7.2% | 8 核口径, 折合单核 13% ~ 58% |
| 堆斜率 | **全部为负** | **全部为负** | 见下 |
| RSS 峰值 | 56 → 165 MB (T=4→12) | 同左 | **启动期瞬态**, 不是稳态 |
| RSS 窗口结束 | **27 → 31 MB** | 同左 | 与 T 基本无关 → 稳态是一条平线 |
| 推理错误 | 0 | 0 | 所有配置零错误 |

**堆斜率为什么是负的?**
每 worker 稳定释放 ≈ 1.37 MB/min 的堆(T=4 → −5.5 MB/min, T=12 → −16.4 MB/min, 严格线性)。
这是 RKNN runtime 建上下文时申请的那批暂存缓冲, 在预热后的前几秒里一次性还给系统 ——
**同一个 T 在不同阶段跑出来的斜率完全一致**(matrix / saturate / dual 三组对得上),
说明它是确定性的"一次性归还", 不是随帧数增长。

> ★ **内存平线结论**: 测量窗口内堆**单调下降**、RSS 收敛到与 T 无关的 27~31 MB、
> 推理零错误 —— 热循环里**没有** malloc/free, 没有泄漏, 没有碎片抖动。
> RSS 峰值(165 MB @ T=12)出现在启动期, 是 NPU 侧权重/DMA 的暂存映射:
> 单模型每 worker 一个 ctx ≈ 3.3 MB 权重 + 11.0 MB DMA; 双模型 ≈ 6.1 MB + 18.8 MB。

## 七、结论与成因分析

### 7.0 一句话

> **T=6(每核 2 个 worker)是吞吐最优点, T=3(每核 1 个)是延迟最优点, T>6 严格有害。**
> **"T>3 会把 CPU 抢占 / DDR 带宽打爆"这条假设, 实测不成立** ——
> CPU 占用全程 1.6%~7.2%(8 核), 堆斜率全程为负, 真正卡住的是**每颗 NPU 核自身的算力**,
> 以及**同核多上下文之间的串行化**。
> 另外, **`RKNN_NPU_CORE_0_1_2`(三核全开)是最差的绑定策略**: 吞吐只有 1/2.6, 延迟高 25 倍。

### 7.1 瓶颈到底在哪: 三步排除

**第一步: 排除 CPU 抢占。**
`auto`/`round` 策略下真实负载的 CPU 只有 1.6%~2.1%(8 核口径, 折合单核 13%~17%),
饱和负载下 T=12 也只有 5.3%~7.2%; 即使是最差的 `all3` 策略、T=12, 也只有 12%。
就算把 12 个 worker + 1 个狂推的 producer 全塞进 8 核, CPU 也远没到需要抢的程度。
**"线程数 > 3 导致 CPU 抢占" —— 不成立。**

**第二步: 排除用户态的内存/带宽问题。**
所有配置的**堆斜率都是负的**(窗口内在缩, 不在涨) → 内存平线成立, 没有泄漏, 也没有碎片抖动。
输入侧的 DDR 带宽也远不是瓶颈: 640×640×3 = 1.2 MB/帧 × 134 fps ≈ **165 MB/s**,
对 RK3588 的 DDR 来说是个零头。

**第三步: 定位到"每颗 NPU 核"。**
饱和负载下, **T=3 时三颗核的占用就已经是 99.6/99.6/99.7%, NPU 总请求时间 299%/300%** ——
也就是说, **三颗核在 T=3 时就已经全满了**, 这就是天花板。
从 T=3 加到 T=12, 核占用一直是 100%, 吞吐从 121.8 爬到 133.4 就再也不动了。

### 7.2 为什么 T>3 加线程不再涨吞吐, 只涨延迟

同一个核上的多个上下文是**串行**跑的(一颗核一次只能算一个任务)。于是:

| 每核 worker 数 | 每核吞吐 | 相对 1 worker | 单帧 M1 延迟 | 排队时间 |
|---|---|---|---|---|
| 1 (T=3) | 40.6 fps | — | 24.7 ms | ≈ 0 |
| 2 (T=6) | **44.5 fps** | **+9.6%** | 45.1 ms | ≈ 20 ms |
| 3 (T=8) | 44.5 fps | +9.6% | 60.1 ms | ≈ 35 ms |
| 4 (T=12) | 44.2 fps | +8.9% | 90.9 ms | ≈ 66 ms |

多出来的线程**没有带来任何新的计算能力**, 只是把同一颗核的请求排成更长的队:
吞吐不动(M1 延迟涨多少, 每核帧率就降多少), 而每一帧的延迟线性变差。

**那 +9.6% 是哪来的?**
每核从 1 个 worker 变成 2 个 worker 时, 驱动每次推理的**非计算开销**
(提交 → 调度 → DMA 取输入 → 算 → 取输出 → 释放)能被另一个上下文的计算掩盖 ——
典型的**双缓冲流水线效应**。所以它有上限, 而且很小: 第三个 worker 开始就一点都加不上了。

> 这解释了为什么主工程 `npu_pool` 的"每核一个 worker"设计是对的:
> 再往上堆 worker, 换来的 9.6% 吞吐要付 85% 的延迟, 而且它不解决主工程真正的瓶颈
> (检测算力本身不够)。

### 7.3 为什么 `RKNN_NPU_CORE_0_1_2` 是灾难

实测吞吐 45.5 ~ 51.2 fps, 是 `round`/`auto` 的 **1/2.6**; e2e P99 723 ~ 913 ms(高 25 倍);
而且**随 T 恶化**(51.2 → 45.5 fps), CPU 占用从 2.9% 涨到 12%。

机理: `RKNN_NPU_CORE_0_1_2` 的语义是"**把这一次推理拆到 3 颗核上并行算**",
不是"让 3 个上下文各自独占一颗核"。对 640×640 的 YOLOv8n 这种小模型:
每层都要跨核同步一次, 拆分带来的同步开销 + 数据搬移 ≫ 并行收益;
而且所有 worker 都抢全部 3 颗核, 驱动要在多个"全核任务"之间仲裁, T 越大抢得越凶,
于是 M1 延迟从 78 ms 一路涨到 267 ms。

> ★ **给主工程的提醒**:
> `--det-core 0,1,2`(掩码 7)≠ "三颗核都用上"。
> 它和 `--det-core 1,2 --ocr-core 0`(每个模型固定钉在自己的核上)是**完全不同的两件事**。
> 如果有人为了"榨干 NPU"把检测配成掩码 7, 吞吐会直接掉到 1/2.6。

### 7.4 丢帧防雪崩: 策略有效, 而且队列深度对吞吐毫无贡献

**unlimited 模式(Producer 以 ~809 万帧/s 狂推)**:
25 秒里推了 **2.02 亿帧, 丢掉 2.02 亿帧(99.998%), 只处理了 3347 帧**,
系统**不崩、不卡、零错误**, 吞吐 133.9 fps, e2e P99 **53.4 ms** —— 和服务时间同量级。

关键: **队列深度在 unlimited 下完全不影响 e2e 延迟**(q=1/64/128 → 74.3 / 73.9 / 75.2 ms),
因为"丢最旧"保证了**被处理的永远是最新帧**, 队列里堆的那 64 帧根本没被处理过。

**限速过载(400 fps 供给 > 134 fps 服务)**: 队列恒满, 此时深度直接换算成延迟:

```
e2e P99 ≈ 队列深度 / 到达速率
q=1   →  1/400 s ≈   2.5 ms(实测 76 ms, 因为还有服务时间)
q=64  → 64/400 s ≈ 160   ms(实测 233 ms)
q=128 →128/400 s ≈ 320   ms(实测 394 ms)
```

**吞吐在 q=1/64/128 之间只差 0.4%(133.4 → 133.9)** —— 队列缓冲对吞吐**零贡献**,
只线性增加延迟。**结论: 缓冲区只该用于吸收突发, 不该用来"攒吞吐"。**

### 7.5 双模型: 识别集中到单核的代价(独立复现主工程的结论)

| 拓扑 | T=6 吞吐 | M1 avg | M2 avg | 核占用 0/1/2 |
|---|---|---|---|---|
| 检测与识别同掩码(散在 3 核) | **89.0 fps** | 41.0 ms | 26.6 ms | 100/100/100 |
| 识别集中 Core0(复刻 `--ocr-core 0`) | 56.8 fps(**−36%**) | 43.5 ms | 62.4 ms(**+134%**) | **78**/35/33 |

> 这**独立复现了主工程 `context.md` §4.3 的结论**:
> "识别核 Core0 明明只有 19% 占用, 却把近景两路各拖了 72~81 ms —— 那是串行化, 不是算力不足。"
> 本测试台在完全隔离的环境里得到同一个机理, 而且把病灶直接照出来了:
> **Core0 的核占用 78%, 另外两颗核只有 33% —— 三颗核里两颗在干等一颗。**
> 把识别钉在单核上, 识别自己的延迟翻倍(26.6 → 62.4 ms), 整条流水线的吞吐掉 36%。
> 行动项与主工程 `context.md` 的 P1 建议一致: **把识别的候选分发到多颗核**,
> 而不是继续优化 Core0。

双模型串联后吞吐也**不随 T 增长**(81.3 → 89.3 → 89.5 → 88.4 fps), 因为两个模型是串行的,
帧率上限 = 1/(M1+M2); 加线程只是让两个模型的延迟一起变差。

### 7.6 落到主工程上的行动项

| # | 结论 | 依据 |
|---|---|---|
| 1 | **不要用 `RKNN_NPU_CORE_0_1_2`(掩码 7)** 做"三核全开" | 吞吐掉到 1/2.6, e2e P99 涨 25 倍(§7.3) |
| 2 | **保持每核 1 个 worker**(主工程现状) | T=3 时三核已 100% 满; 再加 worker 只加延迟(§7.2) |
| 3 | **把识别候选分发到多颗核**, 别钉在 Core0 | 集中单核 → 吞吐 −36%, 识别延迟 +133%(§7.5) |
| 4 | 想要延迟就别用 `round` 硬绑, 用 `auto` | 真实负载下 e2e P99: auto 28.7 ms vs round 38.1 ms(§6.2) |
| 5 | **队列别攒深**: 深度对吞吐 0 贡献, 只加延迟 | q=1/64/128 → 吞吐差 0.4%, e2e P99 差 5 倍(§6.3) |

### 7.7 这份数据**没有**回答的问题(诚实边界)

- **每颗核的 22.5 ms/帧 到底是"算力不够"还是"NPU 内部 DDR 带宽不够"?**
  本测试台答不了 —— 要分开, 需要把模型按不同输入分辨率重新编译做一次分辨率扫描。
  本测试台能确定的是: **这个上限是【每颗核】的, 不是系统级的**
  (加线程加不出新算力), 而且**不来自 CPU、不来自用户态内存、不来自队列**。
- **驱动侧的真实核利用率**: `/sys/kernel/debug/rknpu/load` 需要 root。
  脚本加 `--use-sudo` 可以拿到; 本次结果用的是应用侧口径(§三 已说明两者的差别)。
- **模型相关**: 结论基于 `ebike_int8_rknn2332.rknn`(YOLOv8n INT8 640×640)。
  换模型(如 PP-OCR)时, "每核 2 个 worker" 的收益会变(双模型场景实测每核 25.7 → 29.7 fps,
  **+15%**, 比单模型的 +9.6% 高)—— 因为每次帧里要跑两次推理, 驱动开销被掩盖的机会更多。
