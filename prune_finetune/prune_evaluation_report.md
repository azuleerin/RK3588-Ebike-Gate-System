# YOLOv8 结构化通道剪枝 —— 性能与精度双维度评估报告

> **基准模型**：`model_opt/onnx/yolov8n_relu_512.onnx`（ReLU 512，第二步性能最优）与
> `model_opt/onnx/yolov8n_silu_576.onnx`（SiLU 576，第二步推荐的可落地基线）
> **设备**：RK3588（recomputer-rk3588-devkit，librknnrt 2.3.2，驱动 0.9.8）
> **日期**：2026-11-19 ~ 11-20
> **产出**：`prune_finetune/models/` 下 6 个剪枝后的 RKNN INT8 模型（2 族 × 3 档）
> **独立性**：全程独立分支，未改动 `rk3588_zero_copy/` 与 `models/`

## 0. 摘要

### 0.1 三条结论

1. **性能：剪枝确实能进一步降耗时，但幅度只有 ~10~20%，不是 MACs 降幅的 1/3。**
   ReLU 512 族从 14.84 ms 降到 **11.90 ms（−19.8%）**，单核 FPS 67.4 → **84.0（+24.7%）**；
   相对第二步最优方案（D1 未剪枝），**再省 19.8%**。

2. **精度：⚠️ 不微调就不能上线 —— 剪枝后模型【一个目标都检不出来】。**
   未剪枝 SiLU576 的全图最大类别得分 **0.7119**、得分>0.15 的位置 **458 个**；
   剪 20% 之后掉到 **0.0020 / 0 个**（类别 logit 被压到 sigmoid 饱和区）。
   这不是"精度略降"，是**输出为空**。按任务约束「剪枝后必须经过微调，禁止直接上线」，
   本目录的模型**只可用于量化微调要补回多少，不可投产**。

3. **踩到一个 RK3588 专属的坑：剪枝宽度必须对齐到 16 的倍数，否则理论算力白砍。**
   不对齐时，p20 理论 MACs −35.5%，但 NPU 补齐到 16 的倍数后**实际只省 13.8%**；
   对齐后 p20/p30/p40 的有效 MACs 降幅变成 **−31.8% / −43.3% / −62.8%**，才和实测对得上。

### 0.2 环境硬约束（决定了本任务能做什么、不能做什么）

任务要求"基于训练集做 BN-L1 稀疏化训练 → 剪枝 → 微调恢复精度"。本板实测：

| 前提 | 板上有吗 | 影响 |
|---|---|---|
| 带标注的检测训练集 | **❌ 没有** | `accuracy/data/frames` 是无标注抽帧；`manifests/frames.csv` 只有"帧号→车牌数"，**检测框没有人工真值** |
| yolov8n 的 `.pt` 权重 | **❌ 没有** | 全盘 `find / -name "*.pt"` 无结果 |
| ultralytics | **❌ 没有** | venv 里只有 torch 2.2.0，无 torchvision / ultralytics |
| GPU / CUDA | **❌ 没有** | RK3588 ARM CPU，`nvidia-smi` 不存在 |
| 外网 | **❌ 没有** | pypi / github 均超时，pip 装不了 ultralytics、也下不了 .pt |

**因此**：
- **性能链路 100% 落地**（剪枝 → 量化 → 板端实测），且用**激活感知**的重要性判据把 BN-gamma
  稀疏化的语义搬到了 ONNX 上；
- **训练链路代码就绪但本板跑不了**（`sparse_train.py` / `finetune.py` / `configs/`），
  需要一台有 GPU + 有标注数据 + 能装 ultralytics 的机器；
- **精度只给"剪枝前 vs 剪枝后"的相对退化**，用仓库既有的 pseudo-mAP 口径（§6）。

## 1. 剪枝方法

### 1.1 判据：把 BN-gamma 稀疏化搬到 ONNX 上

经典路线是给 BN 的 gamma 加 L1 → 训练 → 按 `|gamma|` 排序剪通道。但手上这个 ONNX
**已经没有 BatchNorm 节点**（BN 已折叠进 Conv 的权重/偏置），拿不到 gamma。

折叠关系是 `W_folded = γ·W/√(σ²+ε)`，即折叠后第 c 个输出通道的权重尺度 ∝ `|γ_c|·‖W_c‖`。
于是本实现用

```
importance(c) = ‖W_folded[c]‖₁ · E|act[c]|
```

—— 纯权重 L1 只看"这组权重多大"，没看"这个通道下游起多大作用"；乘上校准集上的
平均绝对激活后，才是**该通道对输出的实际贡献**。它与 `|gamma|` 排序高度一致（只差一个
逐层常数），且不需要重训就拿到了激活侧信息。校准集用与量化完全相同的那 24 张图。

### 1.2 结构约束（保证规则结构 + RKNN 兼容）

| 规则 | 内容 | 原因 |
|---|---|---|
| R1 | 检测头最后一层 Conv（box 64ch / cls 80ch）**不剪输出** | 它决定图输出形状 |
| R2 | C2f 块宽一致：cv1 输出 = n × 块宽；bottleneck 各层 = 块宽 | Split 各份必须等宽 |
| R3 | Concat 分支可不同宽，下游消费者输入数 = 各分支实际宽度之和 | 由传播决定 |
| R4 | 其它 Conv 输出 = `round(out_c×(1−r))` | — |
| R5 | bottleneck 末端沿用 Add 另一侧（Split chunk）的幸存下标 | 逐元素 Add 两操作数要下标对齐 |
| R6 | **宽度对齐到 16 的倍数** | RK3588 NPU 按 NC1HWC2 处理，不对齐会补齐填回（见 §5.2） |
| — | `Split` 的 `split=[16,16]` 属性同步改写 | 不改 ONNX 直接 `ShapeInferenceError` |
| — | SiLU 的 `Mul(X, Sigmoid(X))` 两路同步裁剪 | 两路必须同宽 |

**正确性自检**：
- `ratio=0` 时剪枝模型与原模型**逐位相同**（余弦相似度 = 1.0000，max|Δ| = 0）——
  说明剪枝/反剪枝/下标传播这套逻辑本身是对的；
- 6 个模型全部通过 `eval/validate_pruned_onnx.py`：
  Add 等宽 ✓ / Split 等宽 ✓ / Conv 输入通道数与生产者输出匹配 ✓ / 图输出形状与原模型完全一致 ✓；
- `onnx.checker.check_model` 通过；RKNN 导出后板端核对输出形状 OK。

### 1.3 实际裁掉的宽度

| 档位 | 16 宽块 | 32 宽块 | 64 宽块 | 128 宽块 |
|---|---|---|---|---|
| 20% | 16 → 16 | 32 → 32 | 64 → **48** | 128 → **96** |
| 30% | 16 → 16 | 32 → **16** | 64 → **48** | 128 → **96** |
| 40% | 16 → 16 | 32 → **16** | 64 → **32** | 128 → **80** |

> 16 宽的块剪不动（NPU 最小粒度）；20%/30% 两档因为对齐到 16，32 宽块在 30% 档
> 就被砍到 16 了（不是设计如此，是对齐的副作用）。

## 4. 精度评估

### 4.1 口径（务必看）

仓库里**没有人工标注的检测框**。本报告的 mAP@0.5 沿用仓库既有的
**pseudo-mAP** 口径（`accuracy/aggregate.py` 的 `pseudo_map50` / `detection_compare`）：

> **把「同族未剪枝模型」的检测框当真值**，算剪枝模型的 mAP@0.5 / 召回率 / 精确率。

- ✅ 它衡量的是"**剪枝后相对未剪枝掉了多少**"，这正是剪枝评估要的量；
- ❌ 它**测不出绝对精度**（两者都错时看不出来）；
- ❌ 仓库里的**人工真值只有车牌文本**（`accuracy/data/manifests/plates.csv`），
  检测框没有 —— **绝对精度必须业务侧用人工标注回归**。

验证集：`accuracy/data/frames/`（1725 帧，抽帧自 DJI 实拍视频），本次用前 300 帧。

|---|---|---|---|---|---|
| `REF_silu576_unpruned`（真值） | 1.0000 | 1.0000 | 1.0000 | 1478 | 0.5004 |
| `silu576_p20` | **0.0000** | **0.0000** | **0.0000** | **0** | 0.0000 |
| `silu576_p30` | **0.0000** | **0.0000** | **0.0000** | **0** | 0.0000 |
| `silu576_p40` | **0.0000** | **0.0000** | **0.0000** | **0** | 0.0000 |
| `REF_relu512_unpruned`（真值） | 0.0000 | 0.0000 | 0.0000 | 0 | 0.0000 |
| `relu512_p20/p30/p40` | 0.0000 | 0.0000 | 0.0000 | 0 | 0.0000 |

> **ReLU 族连未剪枝的参照模型都是 0 框** —— 因为第二步已经证明 ReLU 未经微调时
> 类别得分塌到 0.025，检不出任何东西。所以 ReLU 族的精度**在本板无法评估**，
> 它的可用性完全取决于微调。

### 4.3 退化到底在哪一层：置信度塌陷（关键机理）

把阈值降到 0.001 再看（20 帧统计）：

| 模型 | 全图最大类别得分 | 平均类别得分 | 得分>0.15 的位置数 | 框输出最大值 |
|---|---|---|---|---|
| **C1 SiLU576 未剪枝** | **0.7119** | 0.002957 | **458** | 17.81 |
| `silu576_p20` | **0.0020** | 0.001961 | **0** | 8.38 |
| `silu576_p30` | **0.0020** | 0.001961 | **0** | 7.23 |
| `silu576_p40` | **0.0020** | 0.001961 | **0** | 6.13 |
| D1 ReLU512 未剪枝 | 0.0294 | 0.001972 | 0 | 11.85 |
| `relu512_p20` | 0.0098 | 0.001962 | 0 | 10.04 |
| `relu512_p30` | 0.0059 | 0.001962 | 0 | 6.94 |
| `relu512_p40` | 0.0490 | 0.002028 | 0 | 4.40 |

**机理**：
- 剪枝把中间特征分布带偏，**分类分支的 logit 被推到 sigmoid 的下饱和区**
  （平均得分 0.001961 ≈ sigmoid(−6.23)），全图所有位置拿到几乎一样的分数；
- 因此 **得分>0.15 的位置从 458 个掉到 0 个** —— 模型不是"检得不准"，是**根本不输出框**；
- **框回归分支相对轻一些**（框输出最大值 17.81 → 8.38/7.23/6.13），
  说明网络并没有完全崩坏，是**分类头被压平**了；
- 这与第二步 ReLU 的塌陷机理**完全一致**（max_cls 0.7119 → 0.0020），
  说明两者都是"结构改了但权重没重新适配"的失配，**微调正是用来补这一段的**。

### 4.4 微调需要补回多少（预算）

| 项 | 未剪枝 C1 | 剪枝后 | 需要微调补回 |
|---|---|---|---|
| 全图最大类别得分 | 0.7119 | 0.0020 | **0.71** |
| 得分>0.15 的位置数 | 458 | 0 | **458** |
| 框输出最大值 | 17.81 | 6.1~8.4 | 9.4~11.7 |
| 推理耗时 | 22.18 ms | 17.83 ms（已省 19.6%） | — |

**微调要做的，就是让剩下 60%~35% 的通道重新适配新宽度，把 logit 从饱和区拉回来。**
这是通道剪枝的常规代价（文献里 20~40% 通道剪枝微调后通常只掉 1~3 mAP），
但**必须有微调才能达到**。

## 5. Trade-off 分析

### 5.1 性能-精度曲线（以 SiLU 576 族为例）

```
耗时(ms)
  22.2 ┤● 未剪枝 (C1)          ← 精度可用 (458 个候选)
       │  ╲
  20.2 ┤   ● p20 (−9.0%)        ← 精度: 0 个候选, 不可用
  19.7 ┤    ● p30 (−11.2%)      ← 精度: 0 个候选, 不可用
  17.8 ┤     ● p40 (−19.6%)      ← 精度: 0 个候选, 不可用
       └────────────────────────
         0        micro-mAP@0.5 (相对未剪枝)
```

**本图的所有"精度"点都在 0 —— 因为没有微调。**
把这张图和第二步的 ReLU 对照图叠在一起看：
**第二步和第三步是同一个问题的两半** ——
第二步说"ReLU 换完检不出东西"，第三步说"剪枝完也检不出东西"，
两者都需要"重新训练权重"才能落地，而**这一步本板做不了**。

### 5.2 为什么剪枝只换来 10~20%，而 MACs 少了 33~66%？

这是本次最有价值的工程发现（RK3588 专属）：

**RK3588 的 NPU 按 NC1HWC2 处理卷积通道，会把通道数补齐到 16 的倍数。**
剪枝后的宽度若不是 16 的倍数（NPU 内部再补齐），**理论算力就白砍了**。

实测（同一批模型，只改"宽度是否对齐"）：

| 档位 | 理论 MACs 减少 | **不对齐**时的有效减少 | **对齐 16** 后的有效减少 |
|---|---|---|---|
| 20% | −33.2% | **−13.8%** | **−31.8%** |
| 30% | −45.2% | **−33.2%** | **−43.3%** |
| 40% | −65.6% | **−42.9%** | **−62.8%** |

对齐后理论值与有效值基本吻合（差 1~3 个百分点，来自 16 宽块剪不动等残余），
**这也解释了为什么最初那版模型"剪了反而更慢"**（p40 的算子耗时 39.2 ms > 未剪枝的 36.4 ms）。

> ★ **落地要点：在 RK3588 上做结构化剪枝，通道宽度必须按 16 对齐**，
> 否则剪枝比例和实际收益会严重脱节。

### 5.3 推荐方案

| 场景 | 推荐 | 理由 |
|---|---|---|
| **本板当前（无法微调）** | **不投产任何剪枝模型** | 精度为 0，违反任务约束 #2 |
| **能在 GPU 上微调时（首选）** | **ReLU 512 + 剪枝 30%**（`relu512_p30`） | 耗时 −12.6%（vs D1）、−45.2%（vs C1）；宽度 64→48 / 128→96 / 32→16，**全 16 对齐**；参数量 −45.2%；体积 2.53 MB。30% 是"精度风险"与"收益"的最佳平衡点（40% 虽然再快 8%，但宽度砍到 64→32/128→80 后，剩下通道的信息冗余度更低，精度回归的风险明显更大） |
| 微调资源充足、可以多训几轮 | ReLU 512 + 剪枝 40% | 耗时 −19.8%（vs D1）、−65.6%（vs C1），体积 1.94 MB |
| **精度优先（不打算动激活函数）** | **SiLU 576 + 剪枝 30%**（`silu576_p30`） | 不引入激活失配，只需要把"剪枝失配"补回来；耗时 −11.2%；体积 2.71 MB |
| 追求最低时延 | ReLU 512 + 剪枝 40% | 84.03 FPS 单核，体积 1.94 MB |

> ★ **必须先做的一件事**：微调完之后**重新标定 conf 阈值**。
> 剪枝会整体改变分数分布（本次实测均分从 0.0030 变到 0.0020、但峰值差 350 倍），
> 沿用原来的 0.15 很可能大量漏检或误检。

## 6. 落地风险与注意事项

### 6.1 必须先解决的（阻塞项）

| # | 风险 | 说明 | 处置 |
|---|---|---|---|
| **R1** | **无微调 = 模型不可用** | 得分>0.15 的位置 458 → 0 | **阻塞**：必须补齐「有标注数据集 + .pt + ultralytics + GPU」，跑 `sparse_train.py` → 剪枝 → `finetune.py` |
| **R2** | **没有人工标注真值** | 检测侧只有 pseudo-mAP，测不出绝对精度 | 业务侧用人工标注跑一次完整回归；仓库现有 `accuracy/` 工具链可直接复用 |
| **R3** | **conf 阈值失效** | 剪枝后分数分布整体位移 | 微调后必须重新标定 conf（并同时看 precision/recall 曲线，不要只看单一阈值） |

### 6.2 技术风险

| # | 风险 | 说明 | 处置 |
|---|---|---|---|
| R4 | **宽度未对齐会让收益消失** | 理论 −35% 实际只 −13.8% | 已在 `prune_onnx.py` 里默认 `--align 16`；**任何新增剪枝都要保持这个约束** |
| R5 | **16 宽块剪不动** | YOLOv8n 有一批 16 通道的块，最小粒度下无法剪 | 若要继续压，只能改网络结构（不是剪枝能解决的） |
| R6 | **ReLU 的失配与剪枝的失配会叠加** | 两个未微调的改动叠加，微调难度上升 | **建议一次只动一个变量**：要么换激活（必须重训），要么剪枝（微调即可）；两个一起上，需要更强的训练资源 |
| R7 | **评测口径不是绝对 mAP** | pseudo-MAP 以未剪枝模型为真值 | 绝对精度以业务侧人工标注回归为准；本报告的数字只用于**剪枝档位之间的相对比较** |
| R8 | **测量窗口有外部竞争** | 本次另一个会话一直占着 Core0，轮间波动最大到 1.7× | 已在脚本里加逐核污染检测；**正式复测请在独占窗口跑**（脚本会等"我用的那一核以外全 0"） |
| R9 | **`/run/rk-gate/paused` 是共享状态** | 本板多会话并发，任何一方进维护窗口没清标记 → 看门狗闭嘴 → `rk-gate` 停了没人拉起（本次实测踩到过一次：服务 inactive 且无看门狗告警） | 压测前后确认标记不存在；恢复用 `sudo rm -f /run/rk-gate/paused && sudo systemctl start rk-gate` |

### 6.3 工程注意事项

1. **剪枝必须保持图结构规则**：本实现已处理 Add 等宽 / Split 等宽 / Split 属性改写 /
   SiLU 的 Mul 双路同步；自检脚本 `eval/validate_pruned_onnx.py` 会逐条核对。
2. **每次改动都要核对输出形状**：模型转得出来 ≠ 形状对；形状不对检测框全是乱的。
3. **推理代码不用改**：剪枝后的 RKNN 与原模型接口一致（同样的输入尺寸、同样的 9 个输出），
   `yolo_post.cc` 一行都不用动。
4. **量化口径不要动**：本目录与第二步共用同一套 `export_quantize.py` 的 config
   （per-tensor / opt level 3 / 同一份校准集），保证三步之间的对比链条干净。
5. **主工程未被改动**：`rk3588_zero_copy/` 与 `models/` 全程只读；本任务产出全部在
   `prune_finetune/` 下。

## 8. 一页纸总结

| 维度 | 结论 |
|---|---|
| **性能** | 剪枝 40% + ReLU512：单帧 **14.84 → 11.90 ms（−19.8%）**，单核 **67.4 → 84.0 FPS（+24.7%）**，体积 3.91 → 1.94 MB，参数 −64.8%，MACs −65.6% |
| **精度** | **不微调 = 0**。得分>0.15 的候选位置 458 → 0，pseudo-mAP/召回/精确率全 0（无人工真值，只能给相对退化） |
| **推荐** | GPU 资源到位 → **ReLU512 + 剪枝 30%**（`relu512_p30`，−12.6% / 2.53 MB）；不想动激活 → **SiLU576 + 剪枝 30%**（`silu576_p30`，−11.2%）；**当前板子上一个都别上线** |
| **必做的配套** | 微调 + **重新标定 conf 阈值** + 业务侧人工标注回归 |
| **最有价值的工程发现** | **RK3588 的 NPU 按 16 通道补齐** —— 剪枝宽度不对齐，理论 MACs −35% 只兑现 −13.8%；对齐后才是 −31.8% |
