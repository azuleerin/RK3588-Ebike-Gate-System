## 3.2 单核极限 —— 两个独立口径互相印证（`thread_bench_report.md`）

`thread_bench` 是为此专门搭的 RK3588 三核 NPU 独立压测台（`thread_bench/`）。

### 口径 B（压测台实测，这是"天花板"最硬的证据）

| T（线程数） | 每核 worker 数 | 吞吐 FPS | **每核 FPS** | 核占用 0/1/2 | NPU 总请求% |
|---|---|---|---|---|---|
| **3** | **1/1/1** | 121.8 | **40.6** | **99.6/99.6/99.7** | **299%** |
| 4 | 2/1/1 | 125.7 | 41.9 | 100/100/100 | 399% |
| 6 | 2/2/2 | 133.4 | 44.5 | 100/100/100 | 599% |
| 12 | 4/4/4 | 132.7 | 44.2 | 100/100/100 | 1204% |

**T=3 时三颗核的占用就已经是 99.6/99.6/99.7%，NPU 总请求 299%/300%** ——
**三颗核在 T=3 时就已经全满了，这就是天花板。**
从 T=3 加到 T=12，核占用一直 100%，吞吐从 121.8 爬到 133.4 就再也不动了。

> **每核吞吐从 40.6 涨到 44.5 fps（+9.6%）之后就不再动了 —— 这就是全部的收益上限。**

### 口径 A（主工程实测）

单帧 NPU 推理 **26.83 ms** → `1000 / 26.83 = **37.3 FPS/核**`
（这条链路含检测 + 识别 + 跟踪 + 几何过滤，来源见 `01_极限吞吐数据.md`）

### 结论

两套**完全独立**的测量互相印证：单颗 NPU 核的算力天花板就在 **37~41 FPS**，
三颗核合计 **120~135 FPS**。主工程四路实测 **93 FPS**（含识别/跟踪）与之同一量级。

> ⚠️ 口径 B 只跑检测模型、不含 OCR，所以单核数字略高（40.6 vs 37.3）。
> 两个数**不要混着讲**。

### 压测台的结论摘要（`thread_bench_README_分析与结论.md` 第七章）

> **T=6（每核 2 个 worker）是吞吐最优点，T=3（每核 1 个）是延迟最优点，T>6 严格有害。**
> **"T>3 会把 CPU 抢占 / DDR 带宽打爆"这条假设，实测不成立** ——
> CPU 占用全程 1.6%~7.2%（8 核），堆斜率全程为负，
> 真正卡住的是**每颗 NPU 核自身的算力**，以及**同核多上下文之间的串行化**。

瓶颈定位用"三步排除"法（详见该文件 §7.1）：
① 排除 CPU 抢占 → ② 排除用户态内存/带宽（堆斜率为负、DDR 165 MB/s 是零头）
→ ③ **定位到"每颗 NPU 核"**。

## 3.3 后处理不是 CPU 瓶颈 —— 一个**否定**结论（`npu_post_bench_result.txt`）

**工具**：`rk3588_zero_copy/build/npu_post_bench`（源码 `src/eval/npu_post_bench.cpp`）
**实测**（本次跑）：

```
① 正确性: 基线 255 个框 / 优化版 255 个框 -> 完全一致 ✓
② 性能(每帧):
   A 基线(现状)             0.375 ms/帧
   B 极简NMS+前置过滤        0.301 ms/帧
   节省                      0.074 ms/帧  (1.25x)
③ 折算成整机 CPU 占用(8 核口径):
   4 路 x 20 fps:  基线 0.4%  ->  优化版 0.3%  (省 0.1 个百分点)
   4 路 x 30 fps:  基线 0.6%  ->  优化版 0.5%  (省 0.1 个百分点)
```

**为什么这个"否定结论"值得讲**：优化前后**检测框完全一致**（255 = 255），
但省下的只有 0.1 个百分点的 CPU —— **说明后处理根本不是瓶颈，投入产出比极低**。
（历史对照：2026-11-18 同工具同参数实测 0.361 ms/帧。）

这条证据的价值在于**排除项**：它和"整机 CPU 仅 14.8%"、
"detwait 36.29 ms > 纯推理 26.83 ms"放在一起，就把瓶颈**唯一地**钉死在 NPU 上。
