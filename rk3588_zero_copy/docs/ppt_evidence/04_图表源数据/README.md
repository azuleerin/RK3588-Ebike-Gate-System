## 4.1 `npu_load_before.csv` —— 一期（NPU 调度重构前）三核负载

| | |
|---|---|
| 板子 | RK3588-GATE-01 |
| 采样器 | `/sys/kernel/debug/rknpu/load`（每 2 秒一次） |
| 原始来源 | `logs/soak_30min/load.csv`，2026-11-18 23:24:40 ~ 23:28:40 |
| 当时核绑定 | 检测 **Core1+Core2** / 识别 **Core0** |
| 采样数 | 132 |

**形态（这就是"畸形"的原文）**：

```
68,96,94      ← Core1 压到 96%, Core2 94%, 而 Core0 只有 68%
70,96,94
67,95,91
75,97,96      ← Core1 顶到 97%
```

**问题在哪**：识别被钉在 Core0，而 Core0 实际只用到 67~83%（它还得跟检测抢）；
真正干重活的**两颗检测核已经被压到 94~97%**。算力用在了错误的核上。

**列**：`t`（Unix epoch 秒）、`npu0`、`npu1`、`npu2`（%）、`fps_total`（四路交付合计）

## 4.2 `npu_load_after.csv` —— 二期（三核全开）三核负载

| | |
|---|---|
| 板子 | RK3588-GATE-01 |
| 采样器 | `/sys/kernel/debug/rknpu/load`（每 15 秒一次） |
| 原始来源 | `01_极限吞吐数据/limit_test_3min.csv`，2026-11-19 18:16:20 ~ 18:19:24 |
| 测试条件 | `--max-fps 0`（解除限帧）极限压测 |
| 核绑定 | 检测 **Core0+Core1+Core2** / 识别 **Core0+Core1+Core2** |
| 采样数 | 12 |

**形态（均衡）**：

```
75,75,74      ← 三核几乎完全打平
74,76,76
74,76,78
76,79,78
```

**效果**：单核不再是瓶颈，三核 72~79% 均分；`detwait` 从 50~62 ms 降到 33~38 ms。

**列**：与 `npu_load_before.csv` **完全一致**（`t,npu0,npu1,npu2,fps_total`），
可直接画在一张图上做前后对照。

> 📌 两个文件的 `t` 都是 Unix epoch 秒，量级不同但格式一致；
> 画前后对照图建议按**采样序号**对齐，不要按时间轴对齐（两段测试不是同时发生的）。

## 4.3 `heap_soak_10min.csv` —— 10 分钟持续压测的内存 / fd / 帧号

| | |
|---|---|
| 板子 | RK3588-GATE-01 |
| 时间 | 2026-11-19 18:21:00 ~ 18:31:00（**满 10 分钟**） |
| 配置 | 生产参数（`--max-fps 20`，三核全开） |
| 采样器 | `/proc/<pid>/fd` 计数 + `/proc/<pid>/status` 的 VmRSS + `gate.log` 统计行里的 heap 与帧号 |
| 采样数 | **60（每 10 秒一次）** |

**列**：`pid`、`time`、`fd_count`、`rss_kb`、`heap_kb`、`ch1_frame`~`ch4_frame`

**结论**：

| 指标 | 结果 |
|---|---|
| **fd 数** | **恒定 166，零波动**（首值=最小=最大=均值） |
| 其中 dma-buf fd | 147 个（MPP 缓冲）—— 修复前这个数会线性涨到 1006 撞 1024 上限 |
| RSS | 均值 230 241 KB |
| 活堆 | 均值 77 673 KB（无持续上涨） |
| 四路帧号 | 1400 → 12 900（全程推进） |
| EMFILE 报错 | **0 条** |

> **fd 数说明**：文档旧值是 165，本次实测 166 —— 差 1 个来自当前进程多打开的一个 fd。
> **关键性质"恒定"不变**，这才是要证明的东西。
