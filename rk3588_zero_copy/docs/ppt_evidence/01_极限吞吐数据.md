## 一、核心结论

| 指标 | 数值 | 口径 / 含义 |
|---|---|---|
| **4 路合计交付 FPS** | **93.06**（均值）<br>**95.10**（峰值）<br>91.80（谷值） | 11 次采样（15 秒间隔），已剔除预热首采 |
| 单帧 NPU 推理耗时 | **26.83 ms** | `npu=` 字段，纯推理不含排队 |
| **detwait（等检测结果，含排队）** | **36.29 ms** | 比纯推理多 **9.5 ms** → 这段就是 NPU 排队 |
| ocrwait（等识别结果） | 61.08 ms | 仅 ch1/ch3 检出文字时才有；ch2/ch4 恒为 0 |
| **NPU 三核（硬件 debugfs 口径）** | **c0 72.4% / c1 73.9% / c2 73.9%** | `sudo cat /sys/kernel/debug/rknpu/load` |
| **NPU（应用侧口径）** | **npu 77.4%**（= npu_core = 三核最高） | 应用自己的 `read_hw_load()`，见下 |
| 应用侧分核 | c0 75.5% / c1 76.7% / c2 76.5% | 同一次采样，非事后估算 |
| 整机 CPU | **14.8%** | 8 核合计，应用侧差分口径 |
| VPU（硬解） | 18.9% | 远未饱和 |
| RGA | 0%（本板无 debugfs 节点） | |
| 源视频合计上限 | 171.5 FPS | **说明 93 FPS 不是被素材限制的** |

### ★ 瓶颈卡在哪里：NPU 推理吞吐，不是 CPU 后处理

判据用**代码自带的判读法**（`src/gate_main.cc:1240` 注释原文）：

> `det_wait`：等检测结果的墙钟（含 NPU 排队）—— **比"推理本身"长，说明 NPU 不够用**；
> 跟"推理本身"差不多，说明慢在别处（解码/RGA/后处理）。

本项目实测：

| 候选瓶颈 | 实测 | 判定 |
|---|---|---|
| **NPU 排队** | detwait **36.29 ms** vs 纯推理 **26.83 ms** | ✅ **就是它**（多出的 9.5 ms 是排队） |
| CPU 后处理 | 整机 CPU 仅 **14.8%** | ❌ 排除 |
| RGA（NV12→RGB） | 2.0 ~ 7.1 ms | ❌ 排除 |
| MPP 硬解（VPU） | 18.9% | ❌ 排除 |
| 视频源帧率 | 合计上限 171.5 FPS，实际只跑 93 | ❌ 排除 |
| 帧率封顶 | `--max-fps 0`，已解除 | ❌ 排除 |

**NPU 三核同时 72~74%**，已经接近饱和但没有打满 —— 这是"排队 9.5 ms"的物理来源：
三核各自都忙，但请求排队等待，必然有空闲间隙。

### 否定实验：并发槽位不是杠杆

| 配置 | 合计 FPS | detwait |
|---|---|---|
| `det_slots=2`（现配置，3 槽/worker × 3 worker） | **95.4** | 34.5 ms |
| `det_slots=4`（4 槽/worker × 3 worker = 12 并发） | 93 ~ 99 | **36.5 ~ 38.6 ms** |

提高并发槽位**吞吐没上去、排队反而变长**。**结论：NPU 算力本身是墙**，
再往上走只能换更快的 NPU 模型或减少每帧计算量 —— 不是调参能解决的。

## 二、两套 NPU 口径的区别（不要混着讲）

| 口径 | 怎么取的 | 本次结果 |
|---|---|---|
| **硬件 debugfs** | `sudo cat /sys/kernel/debug/rknpu/load` → `Core0: 72% Core1: 74% Core2: 74%` | c0 72.4 / c1 73.9 / c2 73.9 |
| **应用侧** | 应用自己的 `rk::read_hw_load()`（`src/engine_ctl.cc`）→ 取三核 **max** 作 headline，分核原值另存 | npu 77.4（= npu_core）<br>c0 75.5 / c1 76.7 / c2 76.5 |

**应用侧口径不是重新实现一遍解析** —— 取数工具 `npu_probe.cpp` **直接链接了应用自己的目标文件**
（`build/CMakeFiles/rk_zero_copy.dir/src/engine_ctl.cc.o`），调用的是应用内部同一个
`rk::read_hw_load()` 函数，因此口径与应用/web 控制台**完全一致**。
（应用侧比 debugfs 略高，是因为两边取样相差约 1 秒，瞬时值有波动。）

## 四、复现方法

```bash
cd /home/seeed/rk_deploy/rk3588_zero_copy
sudo vi config/gate.env
#    GATE_MAX_FPS=0        # 解除限帧（测完务必改回 20）
```
