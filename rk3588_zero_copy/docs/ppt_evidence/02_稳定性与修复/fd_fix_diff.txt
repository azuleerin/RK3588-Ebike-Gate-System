    fix(mpp): 修 dma-buf fd 泄漏(通道 5~8 分钟后静默死掉) + 桩函数签名
    
    ★ 这是长跑发现的既有缺陷: 4 路并发跑 5~8 分钟后, 进程的 fd 数撞到
      1024 上限(其中 1006 个是 /dmabuf), MPP 申请不到 dma-buf ->
      "mpp_dma_heap: ioctl alloc failed for Too many open files" ->
      【通道静默死掉】: 进程还在跑, 但那一路视频不再解码。
      健康检查看不出来, 平时只能靠生产看门狗重启兜底。
    
    根因(mpp_decoder.cc 的背压重试循环):
        if (take_one_frame(&tmp, &tmp_raw, &got_real) && got_real) {
            held_frame_ = tmp_raw;      // ← 直接覆盖
            held_out_ = tmp;
        }
      held_frame_ 是"上一次攒到的帧"。直接覆盖, 上一帧就再也没人 mpp_frame_deinit
      -> 它的 dma-buf fd 永远留在本进程里。
    
      触发链: MPP 输入队列满时进入重试循环(最多 500 次 x 2ms = 1 秒)。
      若 1 秒内队列一直满, 函数带着 held_frame_ 直接 return false;
      下一轮 decode() 的重试循环又取到新帧 -> 覆盖 -> 旧帧泄漏。
      重试循环里【每取一帧就漏一帧】。
    
    修法: 覆盖前先把旧帧 mpp_frame_deinit 掉。
    
    顺带修 mpp_decoder.cc:501 的桩函数签名:
      decode() 多了 void** out_frame 出参, RK_HAVE_MPP=0 的桩少这个参数 -> 编译不过。
    
    验证: 修前 fd 线性上涨(798 -> 869 -> 872 -> 909, 几分钟撞 1024);
          修后 10 分钟长跑 fd 数稳定, 无 EMFILE, 四路全程存活。
