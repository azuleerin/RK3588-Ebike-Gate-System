# 现场环境适配指南

适用场景: 到现场接真实相机 —— 换相机、换机位、换板子之后, 把「检测 + 车牌识别 + IPM 测速 + MQTT 上报」整条链路重新跑通。
目标: 照着本文做, 一小时内拿到「9/9 PASSED」的验收结论。

> 本文只讲现场会变的四件事: **源地址 / IPM 标定 / 车道宽度 / MQTT 与设备号**, 以及一个**已知风险(绿牌)**。
> 其余部分(硬解、零拷贝、内存守卫)默认已经跑通, 出问题查第 6 章速查表。

## 3. 改 RTSP 源

### 3.1 源地址是第一个位置参数(没有 `--rtsp` 选项)

```
./build/rk_zero_copy rtsp://192.168.31.200:8557/h264 model/ebike_int8_rk2332.rknn --labels model/labels_ebike.txt --no-show --decoder mpp ...
```

- `rtsp://<相机地址>:8557/h264` 是**第一个位置参数**, 后面紧跟模型路径 —— **不是 `--rtsp` 选项**
- 换相机 = 只改这一个地址, 其余参数不动
- 端口不是 8557 时整段替换: `rtsp://192.168.31.201:554/live`

### 3.2 怎么确认源通了(板子上, 不依赖 ffprobe)

```bash
cd /home/seeed/rk_deploy/rk3588_zero_copy
export LD_LIBRARY_PATH="$PWD/third_party/lib:$PWD/lib:/usr/lib:$LD_LIBRARY_PATH"

./build/rk_zero_copy \
  rtsp://192.168.31.200:8557/h264 \
  model/ebike_int8_rk2332.rknn \
  --no-show --decoder mpp --frames 30
```

日志里必须按顺序出现这 3 行:

```
视频流: 1920x1080  fps=25.00  codec=h264
[解码] 后端 = Rockchip MPP 硬解 (h264, VPU)
[MPP] 硬解出帧: 1920x1080 stride=1920x1088 dma-buf fd=23
```

| 缺哪一行 | 说明 | 下一步 |
|---|---|---|
| 第 1 行 | RTSP 没连上 | `ping <相机IP>`; 核对地址/端口; 确认相机在推流 |
| 第 2 行显示 `FFmpeg h264` | 硬解没走通 | 加 `--decoder mpp`; 看有没有 `[警告] 没有找到 h264_rkmpp 解码器`(不影响, 本工程硬解走 MPP 库) |
| 第 3 行 | 硬解卡住 | 查第 6 章第 3 行 |

PC 上有 ffprobe 的话也可以直接问相机:

```bash
ffprobe -v error -show_entries stream=width,height,avg_frame_rate -of csv rtsp://192.168.31.200:8557/h264
```

期望: `1920,1080,25/1`

### 3.3 换源时先拿本地 MP4 试跑(排源问题最快)

程序会自动识别本地文件, 并**按源帧率播放**(不会瞬间跑完):

```
./build/rk_zero_copy /home/seeed/rk_deploy/rk3588_zero_copy/DJI_20261102155401_0126_D.MP4 model/ebike_int8_rk2332.rknn --labels model/labels_ebike.txt --no-show --decoder mpp --frames 300
```

本地 MP4 通了、相机不通 → 问题在网络/相机, 不在程序。

## 4. 重新标定测速(IPM)

### 4.1 什么时候必须重标

| 情况 | 动作 |
|---|---|
| 相机换了 / 机位动了 / 相机高度改了 | **必须重标 IPM**(第 4.2 ~ 4.5 步) |
| 机位没动, 只是车道宽度变了 | 至少要重量 `--ipm-width-m`(第 4.6 步) |
| 相机高度/视角变了, 车牌框位置也偏了 | 还要调 `--roi-ratio / --roi-y / --roi-height`(第 4.7 步) |

### 4.2 板子上抓一张现场截图

```bash
python3 - <<'PY'
import cv2
cap = cv2.VideoCapture("rtsp://192.168.31.200:8557/h264")
ok, frame = cap.read()
assert ok, "没读到帧"
cv2.imwrite("/tmp/ipm_shot.jpg", frame)
print("saved", frame.shape)
cap.release()
PY
```

### 4.3 在笔记本上选点(工具在这里跑, 不在板子上)

```bash
scp seeed@192.168.31.77:/tmp/ipm_shot.jpg .
cd /home/seeed/rk_deploy
python3 tools/draw_ipm_points.py ipm_shot.jpg --size 1920x1080
```

- `--size` 填**流水线实际的帧分辨率**(第 2 步日志里的 `视频流: WxH`), 当前是 `1920x1080`
- 截图分辨率和 `--size` 不一致时, 工具会按比例换算, 不用自己算
- 窗口里**依次点 4 个角**; 点错按 `r` 重选, `Esc` / `q` 退出

### 4.4 点选原则

- 点的是**路面上那块标定矩形的 4 个角**, 不是车道线的两端
- **远端那条边 = 画面上方那条边**(相机俯视路面时, 远处在上方)
- 远边和近边都要**贴合实际车道宽度**
- 工具会自动把乱点的 4 个点纠正成板端要的环形顺序, 并在图上用红/绿标出远边/近边:
  `P0 远端左 → P1 远端右 → P2 近端右 → P3 近端左`
- 4 点一旦交叉(打花), 板端就算不出正确焦距, 工具会提示重新选

### 4.5 贴回启动命令

工具最后直接打印可粘贴的一行:

```
--ipm-points "300,622;1500,643;1450,877;550,819"
```

整段替换启动命令里的 `--ipm-points "..."`。

### 4.6 量车道宽度 → `--ipm-width-m`

`--ipm-width-m` = **标定区横跨的实际宽度(米)**, 拿卷尺量标定区那一段车道。
填错会让测速值整体偏(比例偏); 当前标定值是 `3.5`。

### 4.7 换高度/视角后: 调车牌 ROI

`--roi-ratio 0.72 --roi-y 0.70 --roi-height 0.16` 是车牌 ROI 在**车体框内**的位置和大小(按比例)。
换相机高度或视角后这几个值大概率要跟着调 —— 调法: 加 `--save-roi` 跑几十帧, 看 `output_rois/` 里送进 LPRNet 的图是不是完整车牌。

### 4.8 验证标定生效

日志里必须有这两行:

```
[测速] IPM 模式: 标定梯形 300,622;1500,643;1450,877;550,819
[测速] IPM 就绪: f=1288.8px 标定区 3.50m x 7.56m  鸟瞰 350x756 @100px/m  矩形误差=0.000
```

- `矩形误差` **接近 0** → 4 点构成合理矩形, 焦距解算正确
- `矩形误差` 明显大于 0 → 点选有问题(多半是远/近边判反), 回 4.4 重选
- 完全没有这两行 → `--ipm-points` 没传进去, 或不是 4 个点

### 4.9 无显示器时验证工具逻辑

```bash
cd /home/seeed/rk_deploy
python3 tools/draw_ipm_points.py --selftest "300,622;1500,643;1450,877;550,819"
```

只跑「顺序纠正 + 分辨率换算」, 不需要 GUI。

## 5. 绿牌(新能源)认不出 —— 已知风险

### 5.1 现象

- 车牌**能框出来**, 蓝牌/黄牌大多能认出
- **绿牌经常认不出 / 输出乱码**(比如 `E1`、`1`)

### 5.2 根因: 模型训练分布不覆盖 + 字符集没有汉字

**先说已经排除掉的**(别再往这些方向查):

- **不是 INT8 量化把模型打坏了**: 同一块模型在它自己的测试图 `test_plate.jpg` 上
  正常输出 `B12345`(置信度 0.78); 而且 int8 喂法和 float 喂法**都错** ——
  量化问题不会两种喂法同时错。
- **不是现场接线/参数问题**: 蓝牌、黄牌在同���套参数下能认出完整号码。

**真正的原因**(来自 `accuracy/` 精度回归实测, 见 `docs/ACCURACY_REPORT_20261113.md`):

1. **训练分布不覆盖**: 这块绿牌是【新能源样式 + 两行 + 近景】, 超出了这块 LPRNet
   的训练分布。实测整牌准确率 **0.00%**、空输出率 **55.76%**, 输出多为 `E` / `XE`
   这类噪声。
2. **字符集里没有汉字**: LPRNet 的字符集是 `0-9 A-Z` + 少数字母(去掉了容易混的 I/O),
   **省份简称(如"苏")永远输出不了**。所以就算模型认对了号码, 也拼不出完整车牌。

> ⚠️ 另有一个**独立**的坑(与绿牌主因无关, 但换模型时要一起确认):
> 转模型时若把 `mean_values/std_values` **固化进了计算图**, 板端 LPRNet 又按
> `(x-127.5)/127.5` **再归一化一次**, 就成了双重归一化, 输出会被毁掉。
> 代码里已有开关 `PlateRecConfig::norm_baked_in`(默认 `false` = 保持旧行为;
> `true` = 板端只喂原始 0~255 像素, 交由运行时自己量化)。
> **它当前不是通过命令行开启的**, 要翻转需改代码重编 —— 所以"拿到新模型前,
> 先确认这个模型是哪种归一化约定"是必做动作。

### 5.3 短期对策(现场现在就能做)

- **绿牌暂时不作为验收项**, 用**蓝牌/黄牌**做识别验证
- 绿牌问题列入风险清单(R1), 等算法组补样本重训后再验
- 现场不要为了绿牌去乱调 `--conf` / `--roi-*`, 那些参数一动, 蓝牌也会跟着变差

### 5.4 长期对策(算法组)

1. **用绿牌/两行牌样本补训**这块 LPRNet(这是主因), 或直接换成 PP-OCR
   (精度回归实测: PP-OCR FP16 整牌准确率 **86.64%**, 明显优于现在的 LPRNet)
2. **字符集要含省份简称**, 否则拼不出完整车牌
3. 顺带确认新模型是「归一化已固化」还是「需要板端归一化」, 二选一,
   并把 `norm_baked_in` 的默认值定下来(和模型配套, 写进部署说明)

### 5.5 怎么判断「不是系统坏了」

按顺序排除这三步:

1. **检测链路正常**: 日志里 `objs=` 有值、车牌框画出来了 → 解码/推理/后处理都没问题
2. **ROI 裁得对**: 加 `--save-roi` 跑几十帧, 看 `output_rois/` 里送进 LPRNet 的车牌图是不是完整车牌(不是地面、不是半个牌子)
3. **蓝牌能认**: 同一套参数下用蓝牌能认出完整号码 → 识别链路本身是通的, 只有绿牌不行

结论口径: **绿牌认不出 = 已知模型问题, 不是现场接线/参数问题**。现场汇报按这个口径写。

## 6. 常见问题速查表

| 症状 | 先看 | 处置 |
|---|---|---|
| 没有 `视频流:` 那行 | RTSP 地址 / 网络 | `ping <相机IP>`; 核对端口; 相机是否在推流; 改**第一个位置参数** |
| 有 `视频流:` 但后端是 `FFmpeg h264` | 硬解没走通 | 加 `--decoder mpp`; `[警告] 没有找到 h264_rkmpp 解码器` 可忽略(硬解走 MPP 库) |
| 有 `后端 = Rockchip MPP 硬解` 但没有 `[MPP] 硬解出帧` | 硬解卡住 | 重启再看; 出现 `rga: irq handler err!` → ROI 退化成极扁矩形, 调 `--roi-ratio/--roi-y/--roi-height` |
| MQTT 没上报 | broker 通不通 | `timeout 5 bash -c 'echo > /dev/tcp/192.168.31.30/1883' && echo OK`; 不通**不影响推理**(程序每 5 秒自动重连); 换设备要改 `--sn` 和 `--mqtt-topic` |
| 测速恒为 0 | IPM 有没有加载 | 日志里没有 `[测速] IPM 模式` → `--ipm-points` 没传进去或不是 4 个点; 见 4.8 |
| 测速值整体偏 | `--ipm-width-m` | 卷尺重量标定区实际宽度(米), 别用默认值 3.5 顶替 |
| 画面卡顿 / fps 掉下来 | 帧行 `fps= / wait= / dec= / rga= / npu=` | `dec` > 1ms → 硬解没走通; `rga` > 10ms 或日志显示 `[RGA] 输入来源: CPU 映射地址` → 零拷贝失效, 性能掉一半 |
| 每帧 `objs=0` | 模型没检出 | 默认置信度 0.25; 确认 `[NPU] 输入来源: DMA-BUF fd`; 确认模型输入尺寸没改 |
| 找不到模型 / 可执行文件 | 文件在不在 | `ls -la models/*.rknn rk3588_zero_copy/model/*.rknn`; 缺 `build/rk_zero_copy` → `cmake -B build && cmake --build build -j4` |
| 车牌识别出乱码(如 `E1`) | 是不是绿牌 | 已知绿牌问题, 见第 5 章; 蓝牌正常就不用动现场参数 |
| 日志刷太快看不清 | 落盘 | 主程序已接管 stderr 写 `--log-file`; `tail -f /home/seeed/rk_deploy/logs/run.log` |

## 7. 验收清单

### 7.1 一键验收(在工程根目录跑)

```bash
cd /home/seeed/rk_deploy
./run_acceptance_demo.sh --source rtsp
```

- broker 不在默认地址时: `MQTT_HOST=192.168.31.30 ./run_acceptance_demo.sh --source rtsp`
- 脚本会自动探测 broker(先试 `192.168.31.30` / `192.168.31.214`, 再扫 `192.168.31.0/24` 的 1883 端口)
- 换相机后如果地址不是默认的, 改 `scripts/run_acceptance_demo.sh` 里的 `RTSP_URL=` 那一行
- 跑完日志在 `/home/seeed/rk_deploy/logs/demo_run.log`

### 7.2 九项自动判定

| # | 判定项 | 通过标志 |
|---|---|---|
| 1 | MPP 硬解已启用 | 日志有 `[解码] 后端 = Rockchip MPP 硬解` |
| 2 | MPP 硬解出帧 | 日志有 `[MPP] 硬解出帧: 1920x1080 ...` |
| 3 | MQTT 报文发送成功 | 日志出现 N 次 `[MQTT] 报文发送成功` |
| 4 | 推理流水线在推进 | `[frame N]` 的 N 在涨 |
| 5 | IPM 测速已标定 | 日志有 `[测速] IPM 模式: 标定梯形 ...` |
| 6 | LPRNet 车牌模块 | 日志有 `[LPRNet] 已启用: 牌类=1 ...` |
| 7 | 帧守卫 构造/析构 1:1 | 守卫日志 `构造=N 析构=N` |
| 8 | 进程正常退出 | 退出码 0, 无崩溃 |
| 9 | 活堆未失控 | `heap=` < 200MB |

全绿 → 终端打印 `✅ DEMO PASSED`。

### 7.3 现场手动补充验收(脚本管不到的)

- [ ] **车牌**: 用蓝牌过一遍, 抓报文确认 `plate_no` 字段是完整车牌(绿牌按第 5 章处理)
- [ ] **测速**: 让一个目标从标定区穿过, 看报文的 `speed` 字段(单位 km/h), 与手机秒表对一下
- [ ] **上报**: 抓包确认 topic 是 `device/<你改的sn>/message/up/ivs_result`, 报文里的 `sn` 也是同一个
- [ ] **绿牌**: **不作为验收项**, 记进风险清单
