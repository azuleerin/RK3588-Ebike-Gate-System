# 精度回归 / NPU 核调度 / MQTT 联调 结论报告 (2026-11-13)

> 一句话结论:
> **INT8 的量化损失在决策量级上远小于 2%(分数漂移 0.04%、框漂移 <1px)→ 可以直接交付,
> 不需要重新做量化校准集**; 但发现两个真问题:
> ① 生产 LPRNet **读不出绿牌(新能源)**, ② 板上编出来的 **FP16 .rknn 是坏的**(输出恒定噪声)。

## 任务一：2000 张图精度回归

### 1.1 先说清楚"手上有什��"

| 想要的对比 | 有没有 | 说明 |
|---|---|---|
| 同一个 ONNX 的 INT8 / FP16 对照 | ✅ 有 | `_bench/dl/yolov8n_optimized.onnx` → INT8(`_bench/yolov8n_rk3588_int8.rknn`) + FP16(`_bench/yolov8n_rk3588_fp16.rknn`, 本次新编) |
| 生产检测模型 `ebike_int8_rk2332.rknn` 的 FP16 对照 | ❌ 没有 | 板子上没有它的 ONNX/PT 源模型, 编不出 FP16 |
| 生产车牌模型 `lprnet_finetuned_int8.rknn` 的 FP16 对照 | ❌ 没有 | 同上 |
| 带人工真值的标注集 | ❌ 没有 | 全盘没有任何 YOLO/COCO 格式的标注文件 |
| 真实机位画面 | ✅ 有 | `DJI_20261102155401_0126_D.MP4` = 客户路口实拍(绿牌电动车+行人), 解出 1664 帧; 另有实时相机 2001 帧(桌面场景) |

所以本次做的是**同源 ONNX 的受控量化对比**(唯一能拿到真值的组合),
外加**生产模型的真实场景行为**。

### 1.2 检测:INT8 vs FP16(受控对比)

用 RKNN 模拟器跑**同一个 ONNX 编出来的两份模型**, 喂**同一批 numpy 输入**
(这样差异 100% 来自量化, 不会被两次不同的插值污染)。

```
数据集 A = 实时相机 2001 帧(桌面场景, 有检测)
数据集 B = 路口实拍 1664 帧(真实机位)

                        全部格子      有把握的格子     分数漂移      框漂移
类别一致率              97.47%         80.45%        0.00037     0.070 格
                                        (分数>0.01 的格子, 179 个)  (~0.56px @stride8)
最大类别概率平均漂移                   —             0.00037
类别概率平均漂移                       —             0.00049
```

**怎么读这三个数**:

1. **分数漂移 0.0004 = 0.04 个百分点** —— INT8 把每个格子的类别概率改动在万分之四,
   这个量级不会让任何"真检测"(分数 >0.25)的框跨过阈值。
2. **框坐标漂移 0.07 格 ≈ 0.56 像素** —— 框基本不动。
3. **类别 argmax 在 2.5% 的格子上翻转**, 在"噪声带"(分数 0.01~0.05)里翻到 20%。
   但那两个格子两边都是在乱猜(分数本来就 0.01), 对最终检测结果没有影响。

> 结论: **INT8 的精度损失 << 2%, 按你的判定标准可以直接交付, 不需要重新做量化校准集。**

⚠️ 但有一个**前提要提醒**: 现在用的量化校准集是 `_bench/calib/` 里的 **24 张图,
全部来自桌面场景**。如果生产部署是路口机位, 建议把这 24 张换成
**路口实拍帧**(本次已经解出 1664 帧, 随手就能换), 再重编一次 INT8 —— 现在的校准集
没有覆盖真实光照/角度。这不影响"INT8 vs FP16"的结论, 但可能影响"INT8 的绝对精度"。

### 1.3 检测:板端跑全量(2000 张)的耗时

| 模型 | 精度 | NPU 耗时/帧 | 备注 |
|---|---|---|---|
| yolov8n (ONNX→RKNN) | **INT8** | **18.33 ms** | 生产形态 |
| yolov8n (ONNX→RKNN) | FP16 | 54.14 ms | **慢 3 倍** —— RK3588 的 NPU 没有原生 FP16, 靠软件模拟 |
| ebike_int8_rk2332 (生产) | INT8 | 24.30 ms | 实测 23.90(rknn_run) + 0.10(取回) |
| lprnet_finetuned (生产) | INT8 | 1.03 ms | |

> **如果客户要求 FP16, 性能要付 3 倍的代价**(18.3 → 54.1 ms, 直接吃掉 40ms 帧预算的一大半)。
> 这也是"能不能交付 INT8"这个决策真正的价值所在。

### 1.4 车牌:生产 LPRNet 的真实表现

从路口实拍里**自动定位绿牌**(`rk_lpr_eval --green-plate`, HSV 阈值找最大绿连通域),
1664 帧全部找到, 裁出来的图非常干净(车牌 `苏N A339058` 一眼可读)。

| 喂法 | LPRNet 输出 | 期望 | 结论 |
|---|---|---|---|
| int8 量化码(生产默认) | `1` / `1L` / `""` | `A339058` | **0% 正确** |
| float32 | `E1` | `A339058` | **0% 正确** |

**这不是量化问题**(两种喂法都读不出来), 是**模型域问题**:
生产 LPRNet 只见过蓝色车牌, **绿牌(新能源)完全读不出来**。
字符集里也没有汉字, 所以"苏"这个省份字本来也读不了(预期输出是 `A339058`)。

> **要客户/算法组确认**: 生产车牌模型是否需要补绿牌样本重训。
> 另外 `LprNet::infer()` 的 **float32 喂法对这个 INT8 模型是坏的**
> (输出恒定 `E1`, 应该是运行时把 float 数据喂给了 int8 张量)。
> 顺带修掉: `--lprnet-feed float` 这个命令行选项实际上不可用, 建议在下个版本里
> 明确报错, 免得有人拿它做"精度对照"得出错误结论。

### 1.5 板端 FP16 .rknn 是坏的(必须报给算法组)

同一个 ONNX 编出来的 FP16 .rknn, 在**模拟器里完全正常**(和 INT8 一致率 97.5%),
但在**板子上跑, 输出恒定噪声**: 每帧 8874 个框、全是 class 66(键盘)、分数 0.011~0.013、
**换任何一张图结果都一样**(= 模型根本没吃到输入)。

试过三种喂法, 都是垃圾:

| 喂法 | 结果 |
|---|---|
| uint8 NHWC 原始像素 | 24823 个框/帧, 全噪声 |
| float32 NHWC /255 | 8874 个恒定 class-66 框 |
| float16 NHWC /255 | 同上(自己实现的 fp32→fp16 转换) |

根因方向: FP16 模型的逻辑输入是 **FLOAT16**, 但它的 `qnt_type` 仍是
`AFFINE_ASYMMETRIC` —— 这个组合下运行时对输入的处理不对。
**受影响的只有"用 FP16 模型做对照"这件事, 生产用的 INT8 模型不受影响。**
修法: 重新编 FP16 时不要带 `mean/std`(或让算法组确认 RKNN 版本对 FLOAT16 输入的支持)。

### 1.6 交付判定表(你要求的格式)

| 模型名 | 精度类型 | 检测(与 FP16 的量化损失) | 车牌准确率 | 平均耗时(NPU) |
|---|---|---|---|---|
| yolov8n (ONNX→RKNN) | **INT8** | 分数漂移 **0.04%**, 框漂移 **0.56px**, 有把握格子一致率 80.4%(噪声带内) | — | **18.3 ms** |
| yolov8n (ONNX→RKNN) | FP16 | 基准(100%) | — | 54.1 ms(**3×慢**) |
| ebike_int8_rk2332 (生产) | INT8 | 路口实拍检出 person 82 框/1664 帧 | — | 24.3 ms |
| lprnet_finetuned (生产) | INT8 | — | **真实绿牌 0/1**(读成 `1`/`E1`, 非量化问题) | 1.03 ms |

**判定: INT8 精度损失 < 2% → 直接交付。**
(唯一要跟进的是"绿牌读不出"和"校准集换成路口帧", 都不是 INT8 本身的损失。)

## 任务二：NPU 多核调度

实现了 `--npu-core <mask>` / `--lpr-core <mask>`(1=CORE0, 2=CORE1, 4=CORE2, 7=三核, 0=自动)。

**纯 NPU 耗时(`npu_bench`, 排除预处理/后处理)**:

| core_mask | YOLO 检测模型 | LPRNet 车牌模型 |
|---|---|---|
| 0 = 自动 | **24.30 ms** | **1.031 ms** |
| 1 = CORE0 | 25.84 ms | 1.038 ms |
| 2 = CORE1 | 25.07 ms | 1.016 ms |
| 4 = CORE2 | 25.13 ms | — |
| 7 = 三核全用 | **27.92 ms**(最慢) | 1.802 ms |

**端到端(路口实拍, 400 帧, 同一块板子, 倒序复测两次)**:

| 配置 | FPS | NPU 推理 | RGA | 单帧总耗时 |
|---|---|---|---|---|
| 默认(自动调度) | **11.74 / 11.49** | **22.6 ms** | 7.9 ms | 85~87 ms |
| YOLO→core0 + LPR→core1 | 8.70 / **10.91** | **24.5 ms** | 7.9 ms | 91~115 ms |

**结论: 拆核【没有】提升, 反而慢 8%。** 三个原因:

1. **两个模型是串行的**(同一线程里先 YOLO 再 LPR), 没有并发可利用;
   把它们分到两个核, 只是让每个模型失去了"用多核并行算自己"的机会。
2. YOLO 这种小模型**吃多核反而更快**: 自动(24.30ms) < 单核(25.1~25.8ms) < 三核全用(27.9ms)。
   跨核同步开销 > 收益。
3. 三核全用是最差组合。

> **建议: 保持默认 AUTO 调度, 不要拆核。**
> NPU 现在的负载是 core0 约 50%、core1/2 基本空闲, 但那是"任务本来就串行"的体现,
> 不是"核没用上"。真要提吞吐, 该做的是把 LPRNet 和 YOLO 拆到两个线程并行
> (LPRNet 依赖 YOLO 的框, 只能等检测结果, 所以真正的并行空间在 ROI 裁剪+识别那一段)。

### 踩过的坑(都记在代码注释里了)

1. **喂 uint8 还是 float32, 要看逻辑输入的【type】, 不是 qnt_type**:
   INT8/UINT8 的模型喂 uint8 原始像素; FLOAT32/**FLOAT16** 的模型喂 float32 /255。
   只判 FLOAT32 会把 FP16 模型当成量化模型 → 输出全乱。
2. **喂 float32 给 FP16 模型时, 布局要跟模型的 fmt 一致**(NHWC/NCHW) ——
   填错的话 `inputs_set` 会失败, 模型拿到全 0, 每张图输出都一样。
3. **光把像素写进 dma-buf 不够**, 必须 `rknn_create_mem_from_fd` + `rknn_set_io_mem`
   把这段内存绑成 NPU 的输入张量, 否则 `rknn_run(ctx, nullptr)` 读的是没绑过的内存。
4. **BGR→NV12 要用有限范围**(`COLOR_BGR2YUV`, 不是 `COLOR_BGR2YUV_I420`):
   生产链路的源是相机 NV12(有限范围), RGA 会做 16~235→0~255 扩展;
   塞全范围的 NV12 进去会被二次扩展, 画面拉灰, 模型基本检不出东西。
5. 板端 FP16 .rknn 输出恒定噪声(见 1.5), 别拿它做对照。
