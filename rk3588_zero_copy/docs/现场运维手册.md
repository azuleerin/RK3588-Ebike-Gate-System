## 一、排查：系统是不是卡死了？

**一条命令**：

```bash
cd /home/seeed/rk_deploy/rk3588_zero_copy
sudo scripts/gate_health.sh
```

直接给结论：**正常 / 可疑 / 卡死**，并打印服务状态、日志心跳、各路帧号、内存水位、最近告警。

| 结论 | 含义 | 下一步 |
|---|---|---|
| **正常** | 一切正常 | 不用管 |
| **可疑** | 日志或某一路帧号停了一阵 | 再跑一次；持续可疑就看下面的日志 |
| **卡死** | 服务没跑 / 日志停 > 5 分钟 / 某路帧号停 > 3 分钟 | `sudo systemctl restart rk-gate` |

> 看门狗用的就是这套判据 —— 它报"卡死"时会**自动**重启，你手动 restart 只是不放心时再确认一次。

### ⚠️ 看门狗**不会**做什么（重要）

| 情况 | 看门狗的反应 | 原因 |
|---|---|---|
| 进程崩溃 / 被 OOM 杀掉 | **自动拉起** | `Restart=on-failure` + 看门狗双保险 |
| 启动失败（配置错、模型丢） | **带退避自动拉起** | `Result=exit-code` → 判定为"该拉起" |
| 业务卡死（进程活着但不干活） | **自动重启** | L1/L2 心跳判据 |
| **`systemctl stop` 被人为停掉** | **不拉起** | `Result=success` → 判定为"运维有意停的"，尊重意图 |

**所以：有人误 `systemctl stop` 之后忘了 start，服务会一直停着，看门狗不会管。**

**兜底：`gate_health.sh` 会替你叫一声。**

巡检脚本发现「服务不在跑 + 没有维护标记」时，会往 MQTT 发一条 **Level 2 告警**
（"系统已被手动停止，请确认是否为预期操作"），让 Web 控制台弹出来。

| 项 | 说明 |
|---|---|
| 维护标记 | `/run/rk-gate/paused` 或 `/run/maintenance.lock` —— 有任一存在即认为"有人在维护"，**不告警** |
| 去重 | 只在"从有到没"的那一刻发一次，服务恢复后自动重置 |
| 未配 broker | 告警仍会写本地 `/var/log/rk-gate-alerts.log`，但**发不到 Web 控制台** |
| 告警 topic | `device/<SN>/message/up/alarm` |
| 告警分级 | Level 1 = 致命（立即介入）· Level 2 = 警告（需人工确认）· Level 3 = 提示 |

> 所以现场**要么配好 `GATE_MQTT_HOST`**，要么给巡检配一个能收到日志的通道 ——
> 否则这个盲区就真的没人兜了。

## 二、维护与升级

### 1）要停服务做维护（调试、换配置、换模型）

```bash
sudo touch /run/rk-gate/paused     # ① 先让看门狗闭嘴（维护期间它别插手）
sudo systemctl stop rk-gate        # ② 停服务
...                                 # ③ 做你的事
sudo systemctl start rk-gate       # ④ 恢复
sudo rm /run/rk-gate/paused        # ⑤ 解除沉默
```

> **第 ① 步别省**：没有它，看门狗会把停掉的服务又拉起来。
> （单纯 `systemctl stop` 一般不会被拉起，但加了标记是万无一失的做法。）

### 2）改配置（相机地址、模型、帧率、核绑定…）

全部在**一个文件**里，改完重启即可：

```bash
sudo vi /home/seeed/rk_deploy/rk3588_zero_copy/config/gate.env
sudo systemctl restart rk-gate
sudo scripts/gate_health.sh          # 确认起来了
```

### 3）升级程序（换二进制）

```bash
sudo touch /run/rk-gate/paused
sudo systemctl stop rk-gate
# ... 替换 build/rk_gate ...
sudo systemctl start rk-gate
sudo rm /run/rk-gate/paused
```

### 4）改守护配置本身（unit / 看门狗阈值 / 预检项）

```bash
cd /home/seeed/rk_deploy/rk3588_zero_copy
# 改 scripts/systemd/*.service 或 scripts/gate_watchdog.sh
sudo scripts/install_gate_service.sh     # 重装(会 restart 服务)
```

`install_gate_service.sh` 是**幂等**的：反复跑安全，每次都会把 unit 覆盖回仓库里的版本、清掉遗留的 drop-in、重启服务。

### 5）彻底卸载（换回手动跑）

```bash
sudo scripts/install_gate_service.sh --uninstall
```

零残留：unit / logrotate 规则 / 标记文件 / 锁全部清掉。日志默认保留（是证据），要一起删加 `--purge-logs`。

## 三、注意事项

### ⚠️ 开 debug 级别排查问题前，先把日志切到真实磁盘

本板 `/var/log` 是 **47MB 的 zram 内存盘**（不是磁盘），而且 `/var/log/syslog`、
`kern.log` 还在自己长。

平时用 `GATE_LOG_LEVEL=warn`（默认，也是**长期保持**的配置）时，实测日志速率
**398 KB/小时 ≈ 9.5 MB/天**（2026-11-19 封板复测：4 路推理 + 看门狗 + rk-minimal
同时在跑的真实生产配置），47MB 的 zram 完全装得下。

但 **`GATE_LOG_LEVEL=info` 会让帧守卫对每一帧都打日志，
实测 36.5 MB/小时 ≈ 17 GB/天** —— 不到 3 小时就能把 zram 写满，
写满之后应用的 `write()` 会返回 ENOSPC，**服务会崩**。

> ⚠️ 关键点：日志过滤器（`RK_LOG_LEVEL`）只让**默认的 warn 级别**安全，
> 它管不住 info 级别本身。所以"要不要切盘"取决于**你把级别调到哪**，
> 而不是"有没有装过滤器"。**只在真正要开 debug 排查时才临时切盘，排查完立刻切回来。**

**所以要开 debug 级别排查问题时，按这个顺序操作：**

```bash
# ① 先把日志目录切到真实磁盘, 同时开 info 级别
sudo vi /home/seeed/rk_deploy/rk3588_zero_copy/config/gate.env
#    GATE_LOG_DIR=/var/log.hdd
#    GATE_LOG_LEVEL=info
# ② 重装(会把 .service 里的日志路径一起改掉)
sudo scripts/install_gate_service.sh
# ③ 排查……
# ④ 排查完【务必切回来】
sudo vi /home/seeed/rk_deploy/rk3588_zero_copy/config/gate.env
#    GATE_LOG_DIR=/var/log
#    GATE_LOG_LEVEL=warn
sudo scripts/install_gate_service.sh
```

> `/var/log.hdd` 是真实磁盘（journald 就是软链到 `/var/log.hdd/journal` 的）。
> 忘切回来的后果：zram 写满 → 应用 `write()` 失败 → 服务崩溃。

### ⚠️ 兜底：应用侧日志限流（**保命用的，不是让你放心的**）

`log_write()` 里有一个**令牌桶**，默认**每 60 秒最多放行 1000 行**，
超出的直接丢弃并每分钟汇报一次：

```bash
grep Suppressed /var/log/rk-gate-error.log
# [2026-11-19 13:00:34][WARN][log][rate-limit] Suppressed 8152 messages
#   (日志限流: 每 60 秒最多 1000 行, 超出部分已丢弃)
```

> 板端实测（同一台板、同样开 debug 3 分钟）：
> 不限流 = 28043 行 / 吃 4 MB；限流 = 2762 行 / 吃 0.3 MB，**降 90%**。
> 业务统计行（`[ch1][frame N]`）走的是另一条路，**不受限流影响，不会丢**。

#### 🚨 排查完必须切回 `warn`，别把限流当成解决方案

**限流是底线防御，不是根本。** 它压住了 IO 峰值、给人工介入和自愈争取了时间，
但它解决不了"日志该留住却被丢掉"这个问题：

- **被丢掉的往往正是最关键的最后几条。** 现场真出致命 Bug 疯狂刷错时，
  每分钟只有头 1000 条写得出去，之后的**全部静默丢弃** ——
  而崩溃现场最需要的就是**最后那几条**（真正的异常点、触发条件、上下文）。
- 限流一开，**日志就不再是真相**，只是一份"节流版"。据此下结论很容易判错方向。
- 每 60 秒放行 1000 条（约 16 条/秒）足够覆盖常规排障（控制台看、
  抓几十分钟 info 级别数据），但**扛不住底层死循环爆栈、每秒几千条错误**这种量级。

**所以规矩不变：**

```bash
# ① 排查前 —— 先切到真实磁盘, 再开 debug/info
sudo vi /home/seeed/rk_deploy/rk3588_zero_copy/config/gate.env
#    GATE_LOG_DIR=/var/log.hdd        # 真实磁盘, 怎么刷都吃不满内存
#    GATE_LOG_LEVEL=info
sudo scripts/install_gate_service.sh  # 会把 unit + logrotate 的路径一起改掉

# ② 排查中 —— 看日志
tail -f /var/log.hdd/rk-gate-error.log

# ③ 排查完 —— 立刻切回, 别拖到下次
sudo vi /home/seeed/rk_deploy/rk3588_zero_copy/config/gate.env
#    GATE_LOG_DIR=/var/log
#    GATE_LOG_LEVEL=warn
sudo scripts/install_gate_service.sh

# 确认已经切回来了
grep -E "GATE_LOG_DIR|GATE_LOG_LEVEL" \
    /home/seeed/rk_deploy/rk3588_zero_copy/config/gate.env
grep Suppressed /var/log/rk-gate-error.log | tail -1   # 排查期间有丢弃记录
```

> ⚠️ **限流开着 ≠ 可以不切盘。** 限流只保证"盘不会被写爆、进程不会崩"，
> **不保证"你要的日志还在"**。要拿完整的排障证据，唯一的办法是**写到真实磁盘上**。
>
> ⚠️ **systemd 的 `LogRateLimitIntervalSec` 对本服务不生效**（unit 里也写了）——
> 那两条是 journald 的指令，只管走 journal 的输出；本服务是 `append:` 直写文件。
> 板上 A/B 实测：同一份 unit 写 20000 行，append: 文件落了 20000 行，
> 换成 journal 只落 125 行。真正兜底的是上面这个应用侧令牌桶。

#### 为什么是 `60 秒 / 1000 条`

- **常规排障够用**：每秒约 16 条，正常抓几十分钟 info 级别数据完全够用。
- **防灾难有效**：真出现死循环爆栈或每秒几千条错误时，1 分钟只放行 1000 条、
  其余静默丢弃，**把 IO 写入峰值压下来**，给人工介入或自愈机制争取时间。

想调松/调紧（改完要重启服务）：

```bash
# 单位都是"行"，0 = 不限流
sudo systemctl edit rk-gate        # [Service] 段加:
#   Environment=RK_LOG_RATE_LIMIT_BURST=2000
#   Environment=RK_LOG_RATE_LIMIT_INTERVAL_SEC=60
sudo systemctl restart rk-gate
```

> ⚠️ 调大 burst = 更可能留住关键日志，但也更接近写爆 zram 的风险。
> **排查时正确的做法不是调大 burst，而是切到 `/var/log.hdd`。**

### 🚨 应急：zram 被日志写满了怎么办

```bash
df -h /var/log                      # 看剩余
sudo truncate -s 0 /var/log/rk-gate-error.log   # 立刻回收（服务不用停，fd 还在）
```

> **为什么轮转救不了场**：`copytruncate` 要"先复制一份再截断"，需要的空闲空间
> **不小于日志本身的大小**。磁盘快满时它会直接报
> `error writing to ...: No space left on device`，**越满越转不动**。
> 这时唯一的办法就是上面那条 `truncate`（或把日志 `gzip` 到真实盘再清空）。
> 证据留档建议：`gzip -c /var/log/rk-gate-error.log > /home/seeed/rk_deploy/logs/xxx.gz`。

## 四、日志在哪看

| 看什么 | 路径 / 命令 |
|---|---|
| **业务日志**（推理统计、车牌、MQTT） | `/var/log/rk-gate-error.log` |
| stdout（预检结果、启动参数） | `/var/log/rk-gate.log` |
| **看门狗告警**（卡死/重启/水位） | `/var/log/rk-gate-alerts.log` |
| 启动前预检结果 | `/var/log/rk-gate-preflight.log` |
| systemd 层面的日志 | `journalctl -u rk-gate -n 100` |
| 崩溃现场取证包 | `logs/crash_<时间戳>.tar.gz` |

实时跟着看：

```bash
tail -f /var/log/rk-gate-error.log
```

> ⚠️ 本板 journald 是 `Storage=volatile`，**重启即丢** —— 所以业务日志一律落文件，
> 不要只靠 `journalctl` 找证据。
