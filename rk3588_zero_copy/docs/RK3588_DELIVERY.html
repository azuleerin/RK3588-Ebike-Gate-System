第 1 章: 点亮硬件三件套

1.1 MPP 硬解: 版本对齐是生死线

坑: 工程目录里留着旧版 MPP 头文件(20190626), 板子自带的是新版 BSP(1.5.0)。
头文件里定死了结构体布局和 MppApi 函数指针表的顺序 —— **编的时候用旧头, 运行时加载新库,
mpp_create() 之后的第一次调用就按错偏移跳进野地址 → SIGSEGV**。

解法(已固化进 CMakeLists.txt):

# 头文件只从系统目录找, 断掉"从工程目录捡到旧 MPP"的路
find_path(MPP_INC_DIR rk_mpi.h
          PATHS /usr/include/rockchip /usr/local/include/rockchip
          NO_DEFAULT_PATH)
# 库也一样
find_library(MPP_LIB rockchip_mpp
             PATHS /usr/lib/aarch64-linux-gnu /usr/lib /usr/local/lib
             NO_DEFAULT_PATH)
# 工程目录里只要发现 MPP 头文件, 直接 FATAL_ERROR
教训: 第三方头文件/库的版本不一致, 编译期完全看不出来(结构体大小可能碰巧一样),
表现为运行期随机 SIGSEGV。必须在构建系统里做"版本排他检查", 而不是靠人记住。

兜底: MPP 初始化包在 rk::SafeProbe::call() 里(手写 signal handler 捕获 SIGSEGV/SIGBUS),
初始化崩了自动退回软解, 不会带着整机一起挂。

其他 MPP 细节:

  • extradata 不是 Annex-B 时, 部分 rkmpp 版本解析不出 SPS → 启动时告警。
  • 10bit HEVC 不支持(本地 DJI 素材就是 yuv420p10le) → 硬件路直接放弃, 走软解 + CPU 颜色转换。
  • MPP 解出来的图高度会对齐到 16, 用 frame->height 当 NV12 的 plane 高度会导致下半屏花屏。

正确做法: 用 (data[1] - data[0]) / linesize[0] 反推真实行数(见 README 坑①)。

1.2 RGA 零拷贝: 源和目标都必须是真 dma-buf

坑: RGA 的软件 MMU 在 4GB 以上的用户态地址上会失败, 而且失败时会写坏堆
(踩过: 直接把 RGA 目标换成 malloc 内存, 进程随机 abort)。

解法: 整条链路的每一块缓冲都用 dma-buf:

  • 解码帧: MPP 出来的 dma-buf fd
  • RGA 输出: rk::dma_buf_alloc() 出来的 fd
  • NPU 输入: 同一个 fd, 通过 rknn_create_mem_from_fd 绑定给 NPU

任何一端是普通内存, RGA 就退回 OpenCV CPU 转换(功能不丢, 但慢 7.6 倍)。

教训: "零拷贝"不是一句口号, 它是一条端到端的 dma-buf 契约:
解码器 → RGA → NPU, 三段必须共用同一块物理内存, 任何一段断了就退化成拷贝。

1.3 NPU 输入契约: 喂 uint8 还是 float32, 看 type 不看 qnt_type

这是本次最贵的坑(花了几个小时才定位)。

// rknn_tensor_type: FLOAT32=0, FLOAT16=1, INT8=2, UINT8=3
const bool is_float = (attr_logic.type == RKNN_TENSOR_FLOAT32 ||
                       attr_logic.type == RKNN_TENSOR_FLOAT16);   // ★ 别漏 FLOAT16
逻辑输入 type该喂什么喂错的后果
INT8 / UINT8uint8 NHWC 原始像素 [0,255]运行时自己量化, 正常
FLOAT32 / FLOAT16float32 NHWC [0,1](即 /255)喂 uint8 → 输出全乱, 每帧 6000+ 个假框

两个反直觉的点:

  1. FP16 模型的逻辑输入是 FLOAT16(1), 不是 FLOAT32。只判 type == FLOAT32 会把 FP16 模型

当成量化模型 → 喂 uint8 → 输出一片噪声。这就是"板上编出来的 FP16 .rknn 为什么是坏的"。

  1. qnt_type 不能用来判断。FP16 模型的 qnt_type 依然是 AFFINE_ASYMMETRIC,

按 qnt_type 判断必然错。判据是逻辑输入的 type。

配套还有两条:

  • 喂 float32 时布局必须跟模型的 fmt 一致(NHWC 还是 NCHW)。填错的话 inputs_set 会失败,

模型拿到全 0 → 每张图输出都一样, 看着像"模型只输出固定框"。

  • cls 张量已经是概率, 不要再 sigmoid(README 坑⑧)。

1.4 NPU 输入内存要"绑定", 光写进 dma-buf 没用

坑: 只把像素写进 dma-buf, 然后 rknn_run(ctx, nullptr) → 模型读到的是没绑过的内存, 检测框一个都没有。

in_mem = rknn_create_mem_from_fd(ctx, model_fd, model_ptr, model_buf_size, 0);
bind_attr = attr_logic;
bind_attr.pass_through = 0;
bind_attr.type = RKNN_TENSOR_UINT8;
bind_attr.fmt  = RKNN_TENSOR_NHWC;
bind_attr.n_dims = 4;
bind_attr.dims[0] = 1; bind_attr.dims[1] = model_h;
bind_attr.dims[2] = model_w; bind_attr.dims[3] = 3;
rknn_set_io_mem(ctx, in_mem, &bind_attr);      // ★ 这一步不能少

用 RKNN_QUERY_NATIVE_NHWC_INPUT_ATTR + pass_through=1 还能再省一次 NCHW→NHWC 转换。

1.5 RKNN 上下文不能跨线程用

在 A 线程 rknn_init, 拿到 B 线程 rknn_run → 运行时内部死锁(所有线程卡在 futex)。
本次做 NPU 双核并行时踩到: 300 帧卡了 10 分钟毫无动静。

解法: 每个实例的上下文在它自己的工作线程里创建和使用。

教训: 异步/硬件 SDK 的"上下文"通常隐含线程亲和性。文档不一定写, 但一用就死。

第 2 章: 死机排查 (P0-1 / P0-2)

2.1 现象与取证

跑几百帧后整机硬挂死, 无 OOM、无应用崩溃日志, 只有内核侧
rga: irq handler err! INTR[0x2099] + soft reset complete。

2.2 排查方法论: 最小化单元 → 无罪 → 引爆

第一步: 拆成三个只碰一个硬件模块的最小单元(自研 rk_minimal):

单元只碰结论
--decoder-onlyMPP 解码无罪
--rga-onlyRGA 转换无罪
--npu-onlyRKNN 推理无罪

三个都干净 → 必然是多模块交互。

第二步: 主动"引爆"。不靠等它随机崩, 而是写代码故意制造悬垂:
用一个小 dma-buf 占住被释放的 fd 号, 逼 RGA 去 DMA 一个已失效的 fd; 并且把引爆点
挪到 LPR 裁剪之后(RGA 的 DMA 是异步的, 裁剪那一刻还没真正发出去)。

这是本次最有价值的方法论: 被动等崩溃靠运气, 主动引爆能 100% 复现,
而且能把"哪一行之后释放"和"哪一行还在用"精确对齐。

2.3 根因: 悬垂的是 MppFrame, 不是 AVFrame

代码里有一句 av_frame_unref(frame) 在 LPR 裁剪之前, 而 LPR 的 RGA 裁剪用的
是那一帧的 fd —— 帧已经被 unref, fd 可能已被复用, RGA 的异步 DMA 写到了别人的内存。

但真正的问题比这更隐蔽: AVFrame 里是空的(走的 MPP 路径, 像素根本不在 AVFrame 里),
真正悬垂的是 MppFrame。所以只盯 AVFrame 的人会完全看不到问题。

2.4 解法: RAII 守卫 + 极值保护

// 每轮循环一个守卫, 作用域到循环结束 -> 任何 continue/return/异常展开都会释放
rk::MppFrameGuard mpp_frame_guard;   // 托管 MppFrame(结构+缓冲一起)
rk::AVFrameGuard  av_frame_guard;    // 托管 AVFrame

守卫接管所有权, 释放路径只有一条, 不可能漏。同时修掉两个连带问题:

  • wstride 单位错误(应填像素数, 不是字节) —— README 坑②
  • ROI 最小尺寸约束(kMinRoiH=16 / kMinRoiW=32): 检测框退化时 ROI 会变成

780x8 这种极扁的矩形, 纵向放大 6 倍超出 RGA 缩放器承受范围, 硬件直接报错并软复位 core。
实测: 默认参数每 300 帧必现一次, 加高后 900 帧 0 次。

2.5 验证

4.4 小时 / 39 万帧零崩溃, RGA IRQ 错误零新增。

第 3 章: 内存泄漏

3.1 先分清"碎片"和"泄漏"

指标含义判据
VmRSS (from /proc)进程占的物理内存会被 glibc 的 arena 保留/碎片干扰, 会假涨
mallinfo2().uordblks正在使用的堆字节数只增不减才是真泄漏 ✅
struct mallinfo2 mi = mallinfo2();
fprintf(stderr, "... heap=%zuKB ...", (size_t)mi.uordblks / 1024);
教训: 排查内存问题, 第一件事是选对指标。用 RSS 排查泄漏, 会被 malloc 碎片带偏,
白花几天时间。

3.2 排查方法论(四步, 这次真凶就是这么找到的)

  1. 二分法缩小范围: 同一台板子、同一路流, 只换一个变量。

本次: --decoder mpp (+0.049 KB/帧) vs --decoder ffmpeg (+0.612 KB/帧)
→ 泄漏在 FFmpeg 分支, RGA/NPU/跟踪/LPR 全部排除。

  1. 加探针再二分: 在流水线里插临时开关(RK_SKIP=afterdec|afterrga),

把"只跑到解码"和"解码+RGA"分别测一遍 → 泄漏 100% 在解码段。

  1. 写个最小对照程序: 把同样的 60 行逻辑抽出来单独跑 → 不漏。

差异只剩一处: 主程序每帧 av_frame_alloc() 新建帧, 对照程序复用一个。

  1. 去读头文件: av_frame_unref() 的文档原话是

"Unreference all the buffers referenced by frame and reset the frame fields"
—— 它不释放结构体本身, 那是 av_frame_free() 的活。

3.3 真凶

- av_frame_unref(frame_);      // 只放缓冲区, 结构体(416 字节)永远不还
+ av_frame_free(&frame_);      // = unref(缓冲区) + free(结构体)

sizeof(AVFrame) = 416 字节 —— 和实测的 +0.42 KB/帧 完全吻合。

为什么 MPP 硬解路径一直没暴露? 因为它走 MppFrameGuard, 用 mpp_frame_deinit()
把结构和缓冲一起释放了。软解路径每帧一个 AVFrame, 所以必漏。

顺带修掉一个隐藏 bug: 拷贝构造里 av_frame_ref(other.frame_, frame_) 的 dst 是空指针,
av_frame_ref 要往 dst 里写 → 段错误。现在先 av_frame_alloc() 再 ref。

3.4 被证伪的三个假设(省得后人重走一遍)

假设实测结论
送包后不立刻 av_packet_unref(包所有权交给解码器)+0.453 KB/帧 ❌FFmpeg 文档明写 "ownership remains with the caller", 送包后的 unref 必须保留
has_b_frames=0 + LOW_DELAY(关重排序)+0.451 KB/帧 ❌无关
抽干解码器队列释放滞留帧崩溃(TBB abort), 且斜率涨到 +6.1 KB/帧 ❌释放多余帧破坏了 OpenCV 内部状态

3.5 残留的"台阶": 跟踪器 vector 的高水位

SpeedTracker::tracks_ 是 std::vector<Track>, 而 sizeof(Track) ≈ 4.1KB
(里面有 4 组环形缓冲: 速度历史 128×2、显示样本 96×2、像素轨迹 64×3)。
轨迹数涨上去时 vector 扩容 → 一次台阶 +65KB / +129KB(容量 16→32→64)。
这是高水位分配, 不是泄漏, 但会让"活堆直线"看起来有台阶。

结论: 判断泄漏要看尾段斜率, 而不是全程斜率(全程会把台阶算成持续上涨)。

3.6 内存三件套(工程化收尾)

措施作用
--mem-trim-frames/--mem-trim-sec + malloc_trim(0)把 arena 里空闲的还给内核, RSS 不再缓慢爬升
--log-file + 每 5s fdatasync + logrotate copytruncate日志脏页不堆 Page Cache(cgroup 限额满会被 OOM 杀掉, 现场表现像内存泄漏)
fd 台账 + 守卫计数接入业务二进制泄漏/未登记 fd 都能在 [frame] 行一眼看到

第 4 章: 性能诊断 —— 瓶颈在源, 不在算力

4.1 打点

主循环加 t_wait(等流) / t_decode / t_rga / t_npu / t_post / t_total,
外加 src_gap(相邻两帧解码出来的间隔 = 相机真实推送节奏)。

4.2 结论

路径FPS等流解码RGANPU后处理我们的活儿
MPP 硬解24.998.42 ms0.492.3128.330.4631.59 ms (79%)
FFmpeg 软解17.520.38 ms18.4211.4226.370.4856.69 ms (99%)
  • 相机推送 24.98 fps = 40.02 ms, 整帧耗时也是 40.02 ms → 25 FPS 是源的天花板。
  • 但我们的活儿占 79%, 只剩 21% 余量 → 不是"闲着等源"。
  • 换 30fps 的相机, 最多跑到 ~31 fps(31.6ms/帧)。
  • 软解路径是算力打满(99%), 而且 RGA 因为拿到的是 CPU 指针而走慢路(11.42 vs 2.31 ms)。

4.3 必须同时看硬件负载

光看耗时会误判。用 /sys/kernel/debug/rknpu/load(需 root)和 /proc/mpp_service/load:

NPU: Core0 48%  Core1 0%  Core2 0%      ← 单实例默认只用一个核
VPU: rkvdec 1.9%                          ← 硬解几乎空转
CPU: 21.6%
FPS: 25.05

没有任何硬件单元打满, 流水线却卡在 25 FPS → 只能是源。

/proc/mpp_service/load 要先 echo 1000 > /proc/mpp_service/load_interval。
/sys/kernel/debug/rga/load 在本内核不存在(rktop 走别的接口能显示 RGA)。

第 5 章: 精度回归 (INT8 vs FP16)

5.1 能做什么、不能做什么

想要的有没有
同一 ONNX 的 INT8 / FP16 受控对比✅ _bench/dl/yolov8n_optimized.onnx 两份都编出来了
生产模型的 FP16 对照❌ 板上没有它的 ONNX/PT 源模型
带人工真值的标注集❌ 全盘没有任何标注文件

所以只能做同源 ONNX 的受控对比, 而且要用模拟器跑:
板上两个 .rknn 的预处理喂法不同(INT8 收 uint8, FP16 收 float32/255),
像素经过两次不同的插值, 差异会被混进来。模拟器里两个模型吃的是同一个 numpy 数组,
差异 100% 来自量化。

5.2 结论

类别逐格一致率      97.47%
有把握格子一致率     80.45%   (分数>0.01 的格子, 都在噪声带里, 两边都在乱猜)
最大类别概率平均漂移  0.00037  (0.04 个百分点)
DFL 框坐标平均漂移    0.070 格 (~0.56px @stride8)

INT8 的量化损失 << 2%, 可以直接交付, 不需要重做量化校准集。

5.3 顺带发现的两个真问题

  1. 生产 LPRNet 读不出绿牌(新能源)。真实车牌 苏N A339058(字符集里没有汉字,

预期输出 A339058), int8 喂法读成 1, float 喂法读成 E1 ——
两种喂法都错, 所以不是量化问题, 是模型域问题, 要补绿牌样本重训。

  1. 板上编出来的 FP16 .rknn 是坏的: 同一个 ONNX 在模拟器里完全正常, 但在板子上

输出恒定噪声(每帧 8874 个 class-66 框, 换图结果一样 = 没吃到输入)。
三种喂法(uint8 / float32 /255 / float16 /255)全是垃圾。

6.2 三个必须澄清的概念

  1. "交替推理"在数学上不可能提吞吐: 单线程轮流跑两个实例, 总时间还是 2×单次时间。

真正能提吞吐的是并行: 两个实例同时处理相邻两帧(双缓冲流水线)。

  1. CORE_0_1 双核模式 ≠ 把模型拆到两核。它只是"允许用两个核",

而驱动发现这个模型(算子并行度不够)拆不动 → Core1 只占 4%。

  1. 串行流水线分核是负优化: 两个模型本来就轮流占 NPU, 分核只是让每个模型

失去"用多核算自己"的机会(单核跑 YOLO 实测 25ms vs auto 22ms)。

6.3 落地

--npu-pipe 2(默认 1 = 保持原串行路径)。正确性验证: 同一段确定性输入下,
串行与并行的检测结果 15/15 个采样点完全一致。

现在不建议开: 相机只有 25fps, 端到端 FPS 不会变, 白加一个线程和一份内存。
等相机升到 30fps+ 再开(串行路径在 25fps 已占 69% 帧预算, 30fps 就会丢帧;
并行检测能撑到 64fps)。

三、逐个实验的解释

实验 A: YOLO 绑 Core0, LPRNet 绑 Core1 —— 无收益

auto : NPU 24.50 ms(生产 app), 我们的活儿 27.64 ms
A    : NPU 24.50 ms,             我们的活儿 27.64 ms   (完全持平)

原因: 流水线是串行的 —— YOLO 跑完才轮到 LPRNet, 两个模型本来就轮流占用 NPU,
把它们分到两个核, 只是让每个模型失去了"用多核并行算自己"的机会。
实测单核跑 YOLO 反而略慢(22.0~24.6 vs auto 22.0~22.3)。

实验 C: YOLO 绑 RKNN_NPU_CORE_0_1(双核模式) —— 无收益, 也不有害

这是本次最反直觉的结论:

  • rknn_set_core_mask(ctx, RKNN_NPU_CORE_0_1) 确实生效(返回值 0),

但 Core1 的负载只有 4.1% —— 驱动并没有把这个模型拆到两个核上。

  • 原因: 这个模型(yolov8n 级别)的算子并行度不够高, 驱动找不到能并行拆分的部分。
  • 结论: CORE_0_1 对我们这种"小模型 + 单个输入"场景没用,

想要第二个核, 必须自己开两个上下文(实验B)。

⚠️ 第一轮测出来"core0_1 慢 21%"是测量污染 —— 那一轮 rktop 抓屏在同时跑
(它自己在轮询, 抢了 CPU)。重跑 3 轮后是 22.3~22.5ms, 与 auto 持平。
教训: 性能对比绝不能有别的采样进程在旁边跑。

实验 B: 两个 YOLO 实例分绑两核 —— 分两种形态, 只有一种有用

形态做法单帧墙钟FPS判定
B-seq(字面意义的"交替推理")单线程在两个实例之间轮流推理30.2~31.3 ms31.9~33.1❌ 不可能更快: 交替仍是串行, 总工作量没变, 只是把帧分给了两个核; 而单核跑比多核慢, 净效果是变慢
B-par(双缓冲流水线)主线程预处理第 N 帧的同时, 工作线程在跑第 N-1 帧的推理15.4~15.6 ms64.3~65.1✅ 1.95× —— 两个核真正同时满载
关键澄清: 用户设想的"复制成两个实例交替推理"本身不可能提高吞吐 ——
交替执行的总时间 = 2×单次时间, 和一个实例跑两倍帧数一样。
真正能提吞吐的是并行: 两个实例同时处理相邻的两帧(双缓冲)。
这个区别在实现上就是"两个工作线程 + 各自的上下文 + 两块输入缓冲"。

副作用实测说明

5.2 建议

  1. 现在不要开(--npu-pipe 1, 默认): 相机 25fps, 开了端到端 FPS 一样,

只是白白多一个线程和一份内存。收益为零、复杂度上升。

  1. 什么时候开: 相机升级到 30fps 以上时。实测检测阶段能撑到 64fps,

30fps 的源完全够用; 而串行路径在 25fps 的源上已经占 69% 帧预算,
30fps(33ms 间隔)就会开始丢帧。

  1. 实验 C(CORE_0_1)不用再试了 —— 对这个模型无效(Core1 只占 4%)。
  2. 实验 A(两模型分核)也不用再试 —— 串行流水线分核没有意义。

5.3 如果以后真的要用双核, 更值得做的是"拆流水线"而不是"复制模型"

现在的结构是 解码 → RGA → YOLO → 后处理 → LPRNet → 画框 全部串行。
把 RGA 预处理和 LPRNet 识别放到不同的核/线程上并行, 比复制 YOLO 更贴合业务
(而且不需要跑两遍模型)。不过那要先解决"LPRNet 依赖 YOLO 的框"这个依赖关系,
属于架构改动, 不是本次范围。

一、任务 1：FFmpeg 活堆泄漏（结案）

1.1 现象

阶段活堆斜率 (mallinfo2.uordblks)24h 外推
修复前+0.612 KB/帧~997 MB/24h
修复后+0.036 KB/帧（且是阶跃后打平，不是线性）见 1.5

1.2 定位过程（可复现）

  1. 二分法：同一台板子、同一路流，只换解码后端：
解码后端活堆斜率
--decoder mpp（VPU 硬解）+0.049 KB/帧
--decoder ffmpeg（软解）+0.612 KB/帧

→ 泄漏在 FFmpeg 这条分支上（RGA/NPU/后处理/跟踪/LPR 全部排除）。

  1. 拆段探针（临时加 RK_SKIP=afterdec|afterrga 开关）：
  2. 只跑到解码：+0.426 KB/帧 → 泄漏在解码段；
  3. 解码 + RGA：+0.423 KB/帧 → RGA 无辜；
  4. 结论：泄漏 100% 在「取包 + 送解码器 + 取帧」这一段。
  1. 对照实验：把这段逻辑单独抽成一个 60 行的 C 程序（dec_loop），

同样的 av_read_frame → avcodec_send_packet → avcodec_receive_frame → unref，
不漏（+0.03 KB/帧）。差异只剩一处：主程序每帧 av_frame_alloc() 新建一个
AVFrame，而对照程序复用一个。

  1. 对拍 FFmpeg 头文件（/usr/include/aarch64-linux-gnu/libavutil/frame.h）：
av_frame_unref()：Unreference all the buffers referenced by frame and reset the frame fields.
—— 它不释放 AVFrame 结构体本身；那是 av_frame_free() 的活。

sizeof(AVFrame) = 416 字节，和实测的 +0.42 KB/帧 完全吻合。

1.3 真正的修复

src/rk_base/av_frame_guard.cc：

- av_frame_unref(frame_);          // 只放缓冲区, 结构体(416B)永远不还
+ av_frame_free(&frame_);          // = unref(缓冲区) + free(结构体)

顺带修掉一个隐藏 bug：拷贝构造函数里 av_frame_ref(other.frame_, frame_) 的
dst 是空指针（av_frame_ref 要往 dst 里写），现在改成先 av_frame_alloc() 再 ref。

为什么 MPP 硬解路径一直没暴露？因为它走 MppFrameGuard，用 mpp_frame_deinit()
把结构和缓冲一起释放了。软解路径每帧一个 AVFrame，所以必漏。

1.4 被证伪的三个假设（都实测过，斜率一模一样，别再试了）

假设实测结果
送包后不立刻 av_packet_unref（方向 1）+0.453 KB/帧 ❌
has_b_frames=0 + AV_CODEC_FLAG_LOW_DELAY（方向 2）+0.451 KB/帧 ❌
抽干解码器队列崩（TBB abort），且斜率反而涨到 +6.1 KB/帧 ❌

另外，FFmpeg 7.1 的 avcodec_send_packet 文档明确写着
"Ownership of the packet remains with the caller" —— 送包后的 av_packet_unref
必须保留，删掉它不符合 API 语义。

1.5 残余：LPR 车牌缓存（已修）

LprNet::cache_ 是按 track_id 建的 map，而 track_id 单调递增、旧 track 再也不回来，
不清理就只增不减。现在每次写入后按 TTL 删掉过期条目。

1.6 验收

4000 帧实测曲线：

frame    60 -> 1800 :  活堆 21539 -> 21557 KB   (+18 KB, 基本平)
frame  1860        :  一次阶跃 +3066 KB           (帧池高水位, 一帧 1080p NV12)
frame 1860 -> 3960 :  活堆 24623 -> 24622 KB    (完全平, 2100 帧零增长)

结论：活堆不再随帧数线性增长，长跑是一条"偶尔阶跃一次然后水平"的线。

二、任务 3：25 FPS 上限是不是视频源的限制？—— 是

主循环新增打点：t_wait(等流) / t_decode / t_rga / t_npu / t_post / t_total，
外加 src_gap（相邻两帧解码出来的间隔 = 相机实际推送节奏）。

生产路径（MPP 硬解 + RGA + NPU）

相机推送 FPS : 24.98   (解码间隔 40.02 ms)   ← 源就是 25 fps

后处理       : 0.46 ms

我们的活儿   : 31.59 ms  (占帧间隔 79%)

判读：

  • 相机推送间隔 40.02 ms = 精确的 25 fps → 25 FPS 是源的天花板；

  • 就算把相机换成 30 fps，本流水线最多跑到 ~31 fps（31.6 ms/帧）；
  • 最大的单块是 NPU 推理 28.3 ms，其次 RGA 2.3 ms。

软解路径（对照）

流水线 FPS : 17.52    (不是源限制, 是自己跑不动)
解码       : 18.42 ms  (CPU 软解)
