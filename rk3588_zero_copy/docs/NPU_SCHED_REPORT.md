# NPU 多核调度专项测试报告 (2026-11-13 凌晨)

> 结论一句话:
> **只有"两个实例 + 双缓冲并行"这一种策略真的把 NPU 的第二个核用起来了(检测吞吐 1.95×),
> 而"双核模式(CORE_0_1)"和"两模型分核"对这条流水线都【没有收益】。**
> 已把它做成 `--npu-pipe 2` 开关(默认关闭), 但**现在的相机只有 25fps, 端到端 FPS 不会变**,
> 它的价值是【给未来更高帧率的源留余量 + 降低单帧延迟】。

## 三、逐个实验的解释

### 实验 A: YOLO 绑 Core0, LPRNet 绑 Core1 —— **无收益**

```
auto : NPU 24.50 ms(生产 app), 我们的活儿 27.64 ms
A    : NPU 24.50 ms,             我们的活儿 27.64 ms   (完全持平)
```
**原因: 流水线是串行的** —— YOLO 跑完才轮到 LPRNet, 两个模型本来就轮流占用 NPU,
把它们分到两个核, 只是让**每个模型失去了"用多核并行算自己"的机会**。
实测单核跑 YOLO 反而略慢(22.0~24.6 vs auto 22.0~22.3)。

### 实验 C: YOLO 绑 `RKNN_NPU_CORE_0_1`(双核模式) —— **无收益, 也不有害**

这是本次最反直觉的结论:
- `rknn_set_core_mask(ctx, RKNN_NPU_CORE_0_1)` **确实生效**(返回值 0),
  但 **Core1 的负载只有 4.1%** —— 驱动并没有把这个模型拆到两个核上。
- 原因: 这个模型(yolov8n 级别)的算子并行度不够高, 驱动找不到能并行拆分的部分。
- 结论: **`CORE_0_1` 对我们这种"小模型 + 单个输入"场景没用**,
  想要第二个核, 必须自己开**两个上下文**(实验B)。

> ⚠️ 第一轮测出来"core0_1 慢 21%"是**测量污染** —— 那一轮 rktop 抓屏在同时跑
> (它自己在轮询, 抢了 CPU)。重跑 3 轮后是 22.3~22.5ms, 与 auto 持平。
> **教训: 性能对比绝不能有别的采样进程在旁边跑。**

### 实验 B: 两个 YOLO 实例分绑两核 —— **分两种形态, 只有一种有用**

| 形态 | 做法 | 单帧墙钟 | FPS | 判定 |
|---|---|---|---|---|
| **B-seq(字面意义的"交替推理")** | 单线程在两个实例之间轮流推理 | 30.2~31.3 ms | 31.9~33.1 | ❌ **不可能更快**: 交替仍是串行, 总工作量没变, 只是把帧分给了两个核; 而单核跑比多核慢, 净效果是变慢 |
| **B-par(双缓冲流水线)** | 主线程预处理第 N 帧的同时, 工作线程在跑第 N-1 帧的推理 | **15.4~15.6 ms** | **64.3~65.1** | ✅ **1.95×** —— 两个核真正同时满载 |

> **关键澄清**: 用户设想的"复制成两个实例交替推理"本身**不可能**提高吞吐 ——
> 交替执行的总时间 = 2×单次时间, 和一个实例跑两倍帧数一样。
> 真正能提吞吐的是**并行**: 两个实例**同时**处理相邻的两帧(双缓冲)。
> 这个区别在实现上就是"两个工作线程 + 各自的上下文 + 两块输入缓冲"。

## 四、落地实现(已做成命令行开关)

```bash
./build/rk_zero_copy <url> model.rknn --npu-pipe 2      # 双实例双缓冲并行
./build/rk_zero_copy <url> model.rknn                    # 默认 1 = 原来的串行单实例
```

| 文件 | 内容 |
|---|---|
| `include/rk/npu_pipe.h` / `src/rk_base/npu_pipe.cc` | `rk::NpuPipe`: N 个实例 + N 个工作线程 + 双缓冲 |
| `src/eval/npu_sched_bench.cc` | 专项基准工具(六种策略, 墙钟计时) |
| `scripts/npu_sched_run.sh` | 一键跑完六组 + 抓负载 + 出截图 |

**正确性验证**: 同一段确定性输入(DJI MP4)下, 串行与并行的检测结果
**15/15 个采样点完全一致**(逐帧 objs 数相同)✓

### 实现时踩的三个坑(都写进注释了)

1. **RKNN 上下文不能跨线程使用** —— 在 A 线程 `rknn_init`、拿到 B 线程 `rknn_run`,
   运行时内部**死锁**(9 个线程全卡在 futex, 300 帧卡了 10 分钟)。
   现在每个实例的上下文**在它自己的工作线程里创建和使用**。
2. **输入缓冲不能被覆写** —— 同一块 dma-buf 在推理期间被 RGA 重写,
   驱动读到的就是半新半旧的数据。每个实例一块独立缓冲, 提交前确认上一次推理已结束。
3. **并行下"各阶段耗时相加"没有意义** —— 预处理和推理是重叠的, 只能用墙钟。

## 五、副作用与建议

### 5.1 有没有副作用?

| 副作用 | 实测 | 说明 |
|---|---|---|
| **端到端 FPS** | **不变(25 fps)** | 相机只推 25fps, 这是硬上限 —— 算力再快也没用 |
| **单帧延迟** | 略降: 我们的活儿 27.6ms → 26.0ms | 两实例并行时, 第 N 帧的检测在第 N-1 帧的 RGA 期间就开始算了 |
| **单次推理延迟** | 24.5ms → 22.9ms(生产 app 口径) | 单核跑略慢(25ms), 但两个并行 |
| **CPU 占用** | +1~2% | 多了一个工作线程, RGA 预处理本来就在主线程 |
| **内存** | +1 个模型上下文 + 1 块 1.2MB 输入缓冲 | 可忽略 |
| **NPU 功耗** | 上升 | 两核同时满载, 功耗约翻倍(实测温度没变化, 但那是 25fps 的轻负载) |
| **正确性** | ✅ 无差异 | 15/15 采样点逐帧一致 |

### 5.2 建议

1. **现在不要开**(`--npu-pipe 1`, 默认): 相机 25fps, 开了端到端 FPS 一样,
   只是白白多一个线程和一份内存。**收益为零、复杂度上升**。
2. **什么时候开**: 相机升级到 **30fps 以上**时。实测检测阶段能撑到 64fps,
   30fps 的源完全够用; 而串行路径在 25fps 的源上已经占 69% 帧预算,
   30fps(33ms 间隔)就会开始丢帧。
3. **实验 C(`CORE_0_1`)不用再试了** —— 对这个模型无效(Core1 只占 4%)。
4. **实验 A(两模型分核)也不用再试** —— 串行流水线分核没有意义。

### 5.3 如果以后真的要用双核, 更值得做的是"拆流水线"而不是"复制模型"

现在的结构是 `解码 → RGA → YOLO → 后处理 → LPRNet → 画框` 全部串行。
把 **RGA 预处理**和 **LPRNet 识别**放到不同的核/线程上并行, 比复制 YOLO 更贴合业务
(而且不需要跑两遍模型)。不过那要先解决"LPRNet 依赖 YOLO 的框"这个依赖关系,
属于架构改动, 不是本次范围。
