### 1.1 现行 ROI 参数为什么在 fork9 上彻底失效

生产现行参数是在**旧模型的畸形宽扁框**上标定的(框宽 810~902 px、框高 17~167 px),
而 fork9 的框是**整车/全场景框**(实测 f00000: 1835×1040, 覆盖整辆车)。两者语义完全不同:

```
现行:  ROI 宽 = 框宽 × 0.164 = 810×0.164 ≈ 133 px   (旧模型: 框窄而扁, 恰好给出可用宽度)
       ROI 顶边 = 框顶 + 框高×1.0 = 框底            (旧模型: 框扁 => 框底就在车身中部)
fork9: ROI 宽 = 1835×0.164 ≈ 301 px                 (框宽 -> ROI 极宽)
       ROI 顶边 = 8 + 1040×1.0 = 1048 px            (框高 -> ROI 掉到画面下缘, 够不到车身中部的车牌)
```

**实测(f00000, 同一帧同一模型)**:
- 旧模型: 5 个框, 全是扁横条(902×456 / 798×152 / 828×193 / 861×185 / 816×185) → ROI 落在车身中部 → 有机会框到牌
- fork9: 1 个框 1835×1040(整车) → ROI 落到车身底部 → **框不到牌**
- GT 车牌框: (909, 394, 391, 249) —— 位于车身**中部偏右**

### 1.2 离线几何复刻(逐字照抄生产链)

`opt_ebike_fork9/tools/sweep_roi_params.py` 复刻:
`plate_roi_from_box`(main.cc:1119) → `ppocr_pad=0.10` 撑开 → `clamp_roi` → 偶对齐 → `clamp_roi`
→ 最小尺寸(`rh>=16` 向上撑 / `rw>=32` 向两侧撑) → `clamp_roi` → 两行牌切分
(`kTwoRowAspect=2.5`, 上行切分点 `{0.40,0.45,0.50}`, 下行 `0.45` 往下) → 缩放到
`(ceil(48*rw/rh) 上限 320, 48)`(`crop_plate_roi` / `calc_resized_w` 同式)。

## 二、上限验证: PP-OCRv4 能不能读这块两行牌

## 四、O9 残余: 12.26% 的帧顶边仍切进省份字行

- 这 13 帧的 GT 牌宽 **192~380 px**(全部 217 帧牌宽中位 200 px) ⇒ **不是"远处小牌", 是中等距离的牌**
- 成因: 框→牌的相对位置随车辆姿态/距离变化, **单一 `roi_y` 无法覆盖所有帧**
- 影响: 这些帧省份字读不出(但串号仍可读, 整牌命中不受影响)
- 处置建议(需人工决定):
  - 接受 87.74% 的帧首行完整(现参数是 3.12%), 或
  - 若要进一步收敛, 需要**跟随框的时基口径**(即 O9 的根因: 让跟踪器时基与单流版一致)—— 那是**代码改动**, 超出本次"零代码侵入"边界, 需单独授权

## 五、必须如实说明的两条限制

### 5.1 生产二进制**无法直接处理 DJI 这个 MP4**(素材/解码侧问题, 与 ROI 无关)

```
$ 生产二进制 单路跑 DJI:  [MPP] 硬解出帧: 1920x1080 stride=2816x1088
   → 旧模型 cls_max=0.0076, 新模型 cls_max=0.0076  ⇒ 两个模型都只看到"几乎全黑"的输入, objs=0
对照: 能工作的 ch3 素材 → stride=1920x1088
```
⇒ DJI 素材的 MPP 水平 stride 与宽度不一致(2816 vs 1920), RGA 缩放后图像错位。
⇒ 本次**真实车牌端到端评测走的是离线链**(ROI 几何逐字复刻 + 生产同一 PP-OCR),
**没有**用生产二进制直接跑 DJI 视频。
⇒ **这是一个独立于本次任务的发现**: 若现场相机也是这类文件, 生产链路同样会"看不见"。
   板端没有 ffmpeg(`which ffmpeg` 空), `cv2.VideoWriter` 只支持 mp4v(MPP 解码存疑), 本次未能做等价转码验证。

### 5.2 离线链与生产链的差异

| 项 | 离线(本次) | 生产 |
|---|---|---|
| ROI 几何 | 逐字复刻(main.cc / plate_roi.h / gate_main.cc) | 同源 |
| 裁剪与缩放 | `cv::resize` + 同公式 `ceil(48*w/h)` 上限 320 | RGA 同公式 |
| 识别 | **生产同一** `ppocrv4_rec_fp16.rknn` + 字典 + `--ppocr-all` | 同 |
| 候选择优 | 复刻 `better_top_row`(含汉字 > 字符多 > 分数高) | 同 |
| 框的来源 | **原始检测框**(离线) | **跟踪器平滑/预测后的框**(生产) |
| 图像来源 | `accuracy/data/frames/*.jpg`(从 DJI 抽的帧) | MPP 解码帧 |

⇒ 框的来源有差异(跟踪 vs 原始检测), 建议 Step B4 的 300 帧冒烟在**能正常解码的素材**上复验几何,
并用人工抽查裁剪图确认。
