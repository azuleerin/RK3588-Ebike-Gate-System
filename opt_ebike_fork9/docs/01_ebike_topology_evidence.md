# 01 · 生产 ebike 模型的结构证据(从 .rknn 里读出来的, 不是猜的)

> 目的: 手上没有 `best_split.onnx`, 要造一个**结构与生产 ebike 模型完全一致**的
> fork9 候选, 就必须先把生产模型的**真实结构**钉死。
> 本文是那份证据。

---

## 一、证据 A: 权重清单完全对得上

生产 `models/ebike_int8_rk2332.rknn` 内嵌的权重名(用正则扫容器里的
`model.*` 记录名得到)与仓库里 fork9 模板 ONNX 的 initializer 清单对比:

```
RKNN weight records: 128
yolov8n ONNX initializers: 137   (其中 weight/bias 126 个)

=== 在 RKNN 里但不在模板 ONNX 里 (2) ===
  + model.22.dfl.conv.weight
  + model.22.dfl.conv.weight_bias_0
=== 在模板 ONNX 里但不在 RKNN 里 (0) ===
common: 126
```

⇒ **生产模型 = 模板那张网络图 + 2 个 DFL 专属权重**。
DFL 那两个正是"图内 DFL"的东西 —— fork9 形态把它们去掉就对了。

---

## 二、证据 B: 逐算子表给出检测头的真实形状

用 RKNN 运行时的 `RKNN_QUERY_PERF_DETAIL`(`audit/model_audit.py` 的
`runtime_op_table`), 直接读出生产模型每个卷积的权重形状:

```
model.22/cv2.0/cv2.0.0/conv/Conv    (1,64,80,80),(64,64,3,3),(64) -> (1,64,80,80)
model.22/cv2.0/cv2.0.1/conv/Conv    (1,64,80,80),(64,64,3,3),(64) -> (1,64,80,80)
model.22/cv2.0/cv2.0.2/Conv         (1,64,80,80),(64,64,1,1),(64) -> (1,64,80,80)
model.22/cv3.0/cv3.0.0/conv/Conv    (1,64,80,80),(64,64,3,3),(64) -> (1,64,80,80)
model.22/cv3.0/cv3.0.1/conv/Conv    (1,64,80,80),(64,64,3,3),(64) -> (1,64,80,80)
model.22/cv3.0/cv3.0.2/Conv         (1,64,80,80),(2,64,1,1),(2)   -> (1,2,80,80)
model.22/cv3.1/cv3.0.0/conv/Conv    (1,128,40,40),(64,128,3,3),(64) -> (1,64,40,40)
model.22/cv3.1/cv3.1.2/Conv         (1,128,40,40),(2,64,1,1),(2)   -> (1,2,40,40)
model.22/cv3.2/cv3.2.0/conv/Conv    (1,256,20,20),(64,256,3,3),(64) -> (1,64,20,20)
model.22/cv3.2/cv3.2.2/Conv         (1,256,20,20),(2,64,1,1),(2)   -> (1,2,20,20)
```

⇒ **生产 ebike 检测头**:

| 分支 | 第1层 | 第2层 | 输出层 |
|---|---|---|---|
| `cv2` (box, 出 64 通道原始 DFL logits) | [64, C_in, 3, 3] | [64, 64, 3, 3] | [64, 64, 1, 1] |
| `cv3` (cls) | [64, C_in, 3, 3] | [64, 64, 3, 3] | [**2**, 64, 1, 1] |

`C_in` = 64 / 128 / 256(P3 / P4 / P5)。

**与仓库里 fork9 模板(yolov8n, nc=80)逐项对比:**

| | 模板 | 生产 ebike | 一致? |
|---|---|---|---|
| `cv2` 三层 | [64,C_in,3,3] / [64,64,3,3] / [64,64,1,1] | 同左 | ✅ 完全一致 |
| `cv3` 第1层 | [**80**, C_in, 3, 3] | [**64**, C_in, 3, 3] | ❌ 隐藏宽度 80→64 |
| `cv3` 第2层 | [80, **80**, 3, 3] | [64, **64**, 3, 3] | ❌ 同上 |
| `cv3` 输出层 | [**80**, 80, 1, 1] | [**2**, 64, 1, 1] | ❌ nc 80→2, 且吃 64 通道 |

⇒ **唯一的结构差异就是 cls 分支(c3: 80→64, nc: 80→2)**。
所以 `scripts/build_ebike_arch_fork9.py` 只重写 cv3 的 18 个张量, 图结构不动。

## 三、证据 C: 形态C 的输出张量

```
/model.22/Mul_2_output_0     [1, 4, 8400]   scale=2.548393487930298  zp=-128   (box, 像素)
/model.22/Sigmoid_output_0   [1, 2, 8400]   scale=0.0038035186007618904 zp=-128 (cls, 概率)
```

⇒ nc = 2, 锚点数 8400 = 80²+40²+20²。
**这也解释了 runbook 第一节那个坑**: box 的 scale≈2.55(像素量级),
cls 的 scale≈1/255 —— 两个输出**各自量化**, 所以 cls 不会被清零。

fork9 形态下 9 个输出各自量化(scale 都在 1e-3 ~ 1e-1 量级), 实测见
`out/audit_fork9_outputs.txt`。

---

## 四、结论

**生产 ebike 模型 = YOLOv8n 骨干 + nc=2 / c3=64 的检测头 + 图内 DFL 解码 + dist2bbox。**

fork9 改造要做的两件事:
1. 把 `cv2.{i}.2` 的 64 通道原始 DFL logits **直接作为输出**(不再进 DFL 子图);
2. 把 `cv3.{i}.2` 的 2 通道分类 logits 过 Sigmoid 作为输出, 再加一个
   `sum = Clip(ReduceSum(cls, axis=1), 0, 1)`。

这正是瑞芯微 fork `format='rknn'` 的 9 输出形态, 顺序契约
`index = s*3 + {0:box, 1:cls, 2:sum}`(s = 0/1/2 = stride 8/16/32)。
