# YOLOv8 模型改造性能对比报告（SiLU→ReLU × 分辨率下调）

> **基准模型**：`_bench/dl/yolov8n_optimized.onnx`（YOLOv8n，640×640，SiLU）
> **产出模型**：`model_opt/models/`（5 组 + `model_opt/models_ref/` FP16 参考 + per-channel 对照）
> **测试设备**：RK3588（recomputer-rk3588-devkit，librknnrt 2.3.2，驱动 0.9.8）
> **日期**：2026-11-19
> **测试程序**：`model_opt/model_perf_bench.cpp`（零拷贝输入、单核、每轮 30s 稳态、3 轮轮转取中位数）
> **量化口径**：RKNN Toolkit 2.3.2 / w8a8 / **per-tensor** / `optimization_level=3` / 同一份 24 张校准集

## 0. 结论摘要

| 组合 | 单帧平均 | 相对基线 | 单核 FPS | 相对基线 | 体积 | **检测置信度(#>0.15)** | 可用性 |
|---|---|---|---|---|---|---|---|
| **A0** SiLU 640（基线） | **24.580 ms** | — | **40.68** | — | 4.10 MB | **33.6** | ✅ 现状 |
| **B1** ReLU 640 | 17.318 ms | **−29.5%** | 57.74 | **+41.9%** | 3.99 MB | **0** | ❌ **检不出东西** |
| **C1** SiLU 576 | 20.134 ms | **−18.1%** | 49.67 | **+22.1%** | 4.08 MB | **34.2** | ✅ **推荐** |
| **C2** ReLU 576 | 14.595 ms | −40.6% | 68.51 | +68.4% | 3.95 MB | **0** | ❌ 检不出东西 |
| **D1** ReLU 512 | **14.141 ms** | **−42.5%** | **70.71** | **+73.8%** | 3.91 MB | **0** | ❌ 检不出东西 |

**三条核心结论：**

1. **SiLU→ReLU 是性能上最猛的一项（−29.5%），但在不重训的前提下不可用**：
   检测置信度从 0.74 塌到 **0.027**，得分超过 0.15 的位置数从 **33.6 个变成 0 个** ——
   这不是"精度略降"，是**一个都检不出来**。
2. **分辨率下调是当前唯一"既快又安全"的杠杆**：640→576 拿到 **−18.1%**，
   而检测置信度 0.7404→0.7235、候选位置数 33.6→34.2，**基本无损**。
3. **per-tensor 量化在性能上几乎不要钱**（per-tensor 24.580 ms vs per-channel 24.786 ms，
   per-tensor 反而快 0.8%），代价全在精度侧（cls 量化误差 64.4% vs 38.9%），
   精度敏感场景建议改回 per-channel。

> **推荐落地**：本轮先上 **C1（SiLU 576）**，拿 −18.1% 且精度基本不变。
> SiLU→ReLU 留到"允许微调/重训"时再做 —— 它才是真正的大头（可再省 −27%）。

## 1. 实验组设计与改造方法

### 1.1 五组实验

| 组 | 激活 | 分辨率 | 用途 |
|---|---|---|---|
| **A0** | SiLU（原样） | 640×640 | 对照组 |
| **B1** | **ReLU** | 640×640 | 单独测 SiLU→ReLU 的收益 |
| **C1** | SiLU（原样） | **576×576** | 单独测分辨率下调的收益 |
| **C2** | ReLU | 576×576 | 两者叠加 |
| **D1** | ReLU | **512×512** | 继续降分辨率 |
| *REF* | SiLU | 640×640 | per-channel 量化对照（量化 per-tensor 的代价） |

### 1.2 改造怎么做的（两条路径，都不动权重）

**① SiLU → ReLU：ONNX 图手术**

YOLOv8 的 SiLU 在 ONNX 里被展开成 `Mul(X, Sigmoid(X))`（本图实测 **57 对**）。
把这一对换成一个 `Relu(X)` 即可 —— **卷积权重、层数、输出节点全部不变**。

```
改前: Conv ──► X ──┬──► Sigmoid ──┐
                    │              ├──► Mul ──► Y
                    └──────────────┘
改后: Conv ──► X ──────────────────► Relu ──► Y
```

> ★ **只改 57 处**，**保留**了输出端的 3 个 Sigmoid（`/model.22/Sigmoid*`，分类头输出激活，不是 SiLU）。
> ★ 手术是幂等的：`Mul` 的两个输入里若一个是 `Sigmoid` 的输出、另一个正好是该 Sigmoid 的输入，
> 才判定为 SiLU；且要求该 Sigmoid 输出**没有别的消费者**，否则跳过（安全兜底）。

**② 分辨率下调：改 ONNX 输入形状 + 清空输出形状**

```python
inputs['images'].dims = [1, 3, 576, 576]      # 改输入
for o in graph.output: del o.type.tensor_type.shape.dim[:]   # 清空输出形状
```

- ★ **为什么必须清空输出形状**：YOLOv8 头部的 9 个输出在 ONNX 里写死了 `[1,64,80,80]` 这类形状。
  只改输入不改输出，形状就自相矛盾，**模型转出来了检测框也会全是乱的**。
- ★ **为什么改分辨率可行**：YOLOv8 内部的 2 个 `Resize` 用的是**相对 scale `(1,1,2,2)`** 而不是绝对尺寸，
  所以特征图尺寸会跟着输入自动缩放（实测 576→72/36/18，512→64/32/16，全部整除 32，无舍入）。
- ★ 与项目已有的 `_bench/dl/yolov8n_320.onnx` **完全同构**（同样只改输入 + 清空输出形状）。

**⚠ 踩坑记录**：`rknn.load_onnx(input_size_list=[(1,3,576,576)])` 在本 toolkit 2.3.2 上
**被静默忽略**（传 576 出来的还是 640 模型的形状）。必须走上面的 ONNX 改形状路线。
脚本里已去掉 `input_size_list`，并在导出后**逐个模型核对输出形状**，不一致直接标红。

### 1.3 量化口径（5 组完全一致，变量唯一）

```python
rknn.config(mean_values=[[0,0,0]], std_values=[[255,255,255]],   # Rockchip YOLOv8 官方口径
            target_platform='rk3588',
            quantized_dtype='w8a8',            # 权值 INT8 + 激活 INT8
            quantized_algorithm='normal',      # 不用 hybrid(混合精度)
            quantized_method='layer',          # ★ per-tensor (Rockchip 叫 layer)
            optimization_level=3,              # ★ 最高等级图优化
            float_dtype='float16')
rknn.load_onnx(model=onnx)                    # 尺寸已在 ONNX 里改好
rknn.build(do_quantization=True, dataset=calib_list)   # 24 张校准集, 5 组共用
rknn.export_rknn(out)
```

> ★ `optimization_level=3` 是最高等级：算子融合 / 内存复用 / 等效替换全开。
> ★ `quantized_method='layer'` 就是业界说的 **per-tensor**（每个张量一组 scale/zp）；
> 工具链的合法值是 `['layer', 'channel', 'group{SIZE}']`，没有 `'tensor'` 这个写法。

## 2. 板端测试方法

### 2.1 口径

与主工程 `npu_pool.cc:390-395` 严格同构：

```cpp
t0 = now_ms();
rknn_run(ctx, nullptr);
rknn_outputs_get(ctx, n, outs, nullptr);
dt  = now_ms() - t0;          // ← 单帧纯推理耗时
```

- **零拷贝输入**：`rknn_create_mem` + `rknn_set_io_mem`（与生产检测路径同构，不走 `rknn_inputs_set`）
- **单核**：`rknn_set_core_mask(1)`（Core0），组间绝对可比
- **输入尺寸从模型自身查**（`RKNN_QUERY_INPUT_ATTR`），不写死，同一程序跑 640/576/512
- **稳态**：预热 3s → 测 30s → 取该段全部单帧耗时统计

### 2.2 干净窗口（这步踩了个大坑）

生产服务 `rk-gate` 常驻占满 3 个 NPU 核，必须先拿到无竞争窗口：

```bash
sudo touch /run/rk-gate/paused        # 工程自带的维护窗口标记 → 看门狗闭嘴
sudo systemctl stop rk-gate           # 看门狗明确尊重人工 stop (Result=success)
sudo systemctl stop rk-pipeline       # 崩溃复现器在 auto-restart 循环里, 也会抢 NPU
...  测  ...
sudo systemctl start rk-gate && sudo rm /run/rk-gate/paused
```

> ★★ **关键坑**：`/sys/class/devfreq/fdab0000.npu/load` 这个节点在本板 **恒显示 `100@1000000000Hz`**，
> 即使 NPU 完全空闲也一样 —— **不能用它判断空闲**！
> 第一版脚本就是被它坑了：以为已经空闲，其实另一个会话的 `npu_layer_bench` 正在抢 Core0，
> 导致 C1(576) 测出 **49.8 ms**（比 640 的 A0 还慢）这种物理上不可能的数据。
> 正确指标是 `/sys/kernel/debug/rknpu/load`：`NPU load: Core0: 0%, Core1: 0%, Core2: 0%`。
> ★ 改用 debugfs 后重测，并加两道保险：
>   ① 每轮测量时后台采样逐核负载，我只用 Core0，**Core1/Core2 上出现 >10% 就算被污染**；
>   ② 6 个模型**轮转**跑 3 轮（而不是一个跑完再下一个），每组取中位数轮。
> ★ 最终 18 次测量（6 模型 × 3 轮）的"其他核峰值"**全部为 0%**，数据干净。

### 2.3 被测模型的自检（导出后逐个核对）

| 组 | RKNN 输入形状 | 输出形状 | 算子数 | 算子构成（驱动自报） | CPU 占比 |
|---|---|---|---|---|---|
| A0 | [1,640,640,3] NHWC | 80/40/20 三尺度 ✓ | 108 | ConvExSwish×57, Concat×13, OutputOperator×9, Split×8, Add×6, MaxPool×3 | 0.98% |
| B1 | [1,640,640,3] NHWC | ✓ | **102** | **ConvRelu×51, ConvReluAdd×6**, Concat×13, OutputOperator×9, Split×8, MaxPool×3 | 1.49% |
| C1 | [1,576,576,3] NHWC | 72/36/18 ✓ | 108 | ConvExSwish×57, … | 1.34% |
| C2 | [1,576,576,3] NHWC | 72/36/18 ✓ | 102 | ConvRelu×51, ConvReluAdd×6, … | 2.21% |
| D1 | [1,512,512,3] NHWC | 64/32/16 ✓ | 102 | ConvRelu×51, ConvReluAdd×6, … | 1.05% |

> ★ SiLU→ReLU 的机理一目了然：NPU 侧的融合算子从 `ConvExSwish`（含 Sigmoid 指数运算）
> 变成 `ConvRelu`（纯比较），而且 **6 个 Add 被一并融进 `ConvReluAdd`**，算子总数 108→102。

## 3. 性能对比结果

### 3.1 主表（单核 mask=1，零拷贝，30s × 3 轮，取中位数轮）

| 组 | 平均 ms | 中位 ms | **P95 ms** | P99 ms | **单核 FPS** | 模型体积 MB | 轮间范围 ms |
|---|---|---|---|---|---|---|---|
| **A0** SiLU 640 | 24.580 | 25.037 | 27.915 | 28.682 | **40.68** | 4.10 | 23.77 ~ 24.72 |
| **B1** ReLU 640 | 17.318 | 17.780 | 19.031 | 19.362 | **57.74** | 3.99 | 17.11 ~ 17.38 |
| **C1** SiLU 576 | 20.134 | 20.358 | 23.891 | 24.644 | **49.67** | 4.08 | 19.93 ~ 20.75 |
| **C2** ReLU 576 | 14.595 | 14.536 | 18.469 | 19.841 | **68.51** | 3.95 | 14.25 ~ 14.61 |
| **D1** ReLU 512 | **14.141** | 14.531 | **16.433** | 16.941 | **70.71** | 3.91 | 14.07 ~ 14.71 |
| *REF* per-channel 640 | 24.786 | 25.139 | 28.073 | 28.839 | 40.34 | 4.13 | 24.52 ~ 26.11 |

> 轮间范围全部 ≤ 2.3 ms（≤10%），数据稳定。

### 3.2 各项优化的收益

**① SiLU → ReLU（同分辨率对比）**

| 对比 | 平均耗时 | 收益 | FPS 收益 | 仅算力(rknn_run)收益 |
|---|---|---|---|---|
| A0 640 SiLU → B1 640 ReLU | 24.580 → 17.318 ms | **−29.5%** (−7.26 ms) | 40.68 → 57.74 (**+41.9%**) | 19.707 → 12.580 ms (**−36.2%**) |
| C1 576 SiLU → C2 576 ReLU | 20.134 → 14.595 ms | **−27.5%** (−5.54 ms) | 49.67 → 68.51 (+37.9%) | 16.507 → 10.645 ms (−35.5%) |

**② 分辨率下调（同激活对比）**

| 对比 | 平均耗时 | 收益 | FPS 收益 | 仅算力收益 |
|---|---|---|---|---|
| A0 640 SiLU → C1 576 SiLU | 24.580 → 20.134 ms | **−18.1%** (−4.45 ms) | 40.68 → 49.67 (**+22.1%**) | 19.707 → 16.507 ms (−16.2%) |
| B1 640 ReLU → C2 576 ReLU | 17.318 → 14.595 ms | **−15.7%** (−2.72 ms) | 57.74 → 68.51 (+18.6%) | 12.580 → 10.645 ms (−15.4%) |
| C2 576 ReLU → D1 512 ReLU | 14.595 → 14.141 ms | −3.1% (−0.45 ms) | 68.51 → 70.71 (+3.2%) | 10.645 → 8.574 ms (**−19.5%**) |

> ★ 576→512 这一步在**总耗时**上只省 3.1%，但在**纯算力**上省 19.5% ——
> 因为总耗时里混进了一大块**与模型无关的固定开销**（见 §3.3）。如果按算力口径算，
> **512 比 576 更划算**。

**③ 组合最优方案**

| 组合 | 平均耗时 | 总降幅 | FPS | FPS 增幅 |
|---|---|---|---|---|
| A0（基线） | 24.580 ms | — | 40.68 | — |
| **C1** SiLU 576 | 20.134 ms | **−18.1%** | 49.67 | +22.1% |
| C2 ReLU 576 | 14.595 ms | −40.6% | 68.51 | +68.4% |
| **D1** ReLU 512 | **14.141 ms** | **−42.5%** | **70.71** | **+73.8%** |
| *（按算力口径）* D1 | 8.574 ms | **−56.5%** | — | — |

> ★ **理论最大降幅 42.5%（总耗时口径）/ 56.5%（纯算力口径）**，即从 40.68 FPS 提到 70.71 FPS。

### 3.3 一个必须说明的口径问题：`outputs_get` 的固定开销

本模型的 ONNX 有 **9 个输出**，其中 3 个是 `onnx::ReduceSum_*` 的**调试残留张量**
（`[1,80,80,80]` = 51.2 万元素）。`rknn_outputs_get` 要把这些 int8 全部反量化成 float32，
**固定吃掉 3.6 ~ 5.6 ms**，与模型大小无关：

| 组 | 总耗时 | rknn_run | outputs_get | outputs_get 占比 |
|---|---|---|---|---|
| A0 640 | 24.580 | 19.707 | **4.874** | 19.8% |
| B1 640 | 17.318 | 12.580 | 4.738 | 27.4% |
| C1 576 | 20.134 | 16.507 | 3.627 | 18.0% |
| C2 576 | 14.595 | 10.645 | 3.950 | 27.1% |
| D1 512 | 14.141 | 8.574 | **5.567** | 39.4% |

> ★ 这解释了为什么 576→512 在总耗时上只省 3.1%：算力省了 2.07 ms，但输出取回的开销
> 反而多了 1.6 ms（512 的输出虽然更小，但反量化次数/内存访问模式不同）。
> ★ **生产环境的模型（`ebike_int8_rk2332.rknn`）只有 2 个小输出，
> `outputs_get` 实测仅 0.09~0.25 ms**。所以这张表里的"总耗时"包含了本测试模型特有的
> 调试输出开销；**若把调试输出从导出里去掉，D1 的总耗时会掉到约 8.7 ms（相对 A0 的 19.8 ms 约 −56%）**。
> ★ 另外：YOLOv8 的 9 输出里只有 3 个是真正的检测输出（box + cls），
> 生产导出本来就该只保留必要输出。

### 3.4 per-tensor vs per-channel（量化方式对性能的影响）

| 组 | 平均耗时 | FPS |
|---|---|---|
| A0 per-tensor 640 | 24.580 ms | 40.68 |
| REF per-channel 640 | 24.786 ms | 40.34 |

**差异仅 0.8%（per-tensor 反而略快）** —— 量化方式不影响算力（算子数、内存访问、算子类型都一样）。
所以任务要求的 per-tensor **在性能上基本免费**，代价全在精度侧（见 §4.2）。

## 4. 量化误差分析与精度风险提示

> ★ 本节只给**可量化的健康信号**，不替代业务侧的精度回归。

### 4.1 量化误差（INT8 vs 同分辨率 FP16 参考模型，同一批校准图）

参考模型由同一脚本、同一分辨率、`do_quantization=False` 构建，**比出来的差异纯粹来自量化**。
归一化用 FP16 的最大绝对值（不用量程 —— 这批输出里有 `Clip(ReduceSum)` 这种量程退化的辅助张量，
用 range 归一化会算出 100 倍以上没有物理意义的数）。

| 组 | box 张量最大误差 | cls 张量最大误差 | box 平均绝对误差 |
|---|---|---|---|
| A0 SiLU 640 | 55.06% | 64.44% | 0.2021 |
| B1 ReLU 640 | **12.19%** | 60.31% | **0.0548** |
| C1 SiLU 576 | 52.56% | 54.94% | 0.1957 |
| C2 ReLU 576 | 13.06% | 62.76% | 0.0550 |
| D1 ReLU 512 | 13.69% | 56.13% | 0.0554 |
| *REF* per-channel 640 | 55.93% | **38.87%** | — |

> ★ ReLU 版的**量化误差反而更小**（box 12~14% vs 52~55%）——
> 因为 ReLU 把负半轴削平，分布更规整、对 per-tensor 量化更友好。
> ★ 但 **cls 张量的误差在 55~64%**，per-channel 能降到 38.9% —— 这是 per-tensor 的真实代价。
> ★ 上面这几组模型跑的是 **COCO 的 yolov8n**（80 类），与生产的 e-bike 模型不同，
> 误差绝对值不可直接横向对比。

### 4.2 ⚠ 检测置信度：SiLU→ReLU 在不重训前提下是**不可用**的

用 8 张校准图统计"全图最大类别得分"和"得分超过阈值的位置数"
（本项目 conf 阈值就是 0.15）：

**FP32 ONNX（排除量化影响）**

| 变体 | max_cls | 得分 >0.15 的位置数 | 得分 >0.25 的位置数 |
|---|---|---|---|
| SiLU 640 | **0.7727** | 35.9 | 29.1 |
| SiLU 576 | 0.7640 | 39.4 | 31.2 |
| SiLU 512 | 0.7460 | 36.9 | 29.5 |
| ReLU 640 | **0.0250** | **0.0** | **0.0** |
| ReLU 576 | 0.0253 | **0.0** | **0.0** |
| ReLU 512 | 0.0251 | **0.0** | **0.0** |

**交付的 INT8 RKNN 模型（板端实测）**

| 组 | max_cls | 得分 >0.15 | 得分 >0.25 | 判定 |
|---|---|---|---|---|
| **A0** SiLU 640 | 0.7404 | 33.6 | 27.8 | ✅ 正常 |
| **B1** ReLU 640 | 0.0267 | **0.0** | **0.0** | ❌ **检不出任何东西** |
| **C1** SiLU 576 | 0.7235 | **34.2** | 28.0 | ✅ 正常（甚至比 A0 略好） |
| **C2** ReLU 576 | 0.0275 | **0.0** | **0.0** | ❌ 检不出任何东西 |
| **D1** ReLU 512 | 0.0265 | **0.0** | **0.0** | ❌ 检不出任何东西 |

**机理**：SiLU 允许负值（负半轴斜率非零），ReLU 直接把负值削成 0。
YOLOv8 是为 SiLU 训出来的，换成 ReLU 后中间特征大量归零，
**分类分支的 logit 被压到 −3.6 附近**（sigmoid ≈ 0.027），全图所有位置拿到的类别分数几乎一样，
**任何常规阈值（0.15/0.25）下都检不出目标**。这是**结构失配**，不是量化问题
（FP32 和 INT8 表现一致）。

### 4.3 精度风险提示（给业务侧）

| 改造 | 风险等级 | 说明 | 建议 |
|---|---|---|---|
| **640 → 576** | 🟢 **低** | max_cls 0.7404→0.7235（−2.3%），候选位置数 33.6→34.2，量化误差 cls 64.4%→54.9%。小目标可能漏检，大目标基本无损 | **建议业务侧跑一次回归**，重点看小目标/远距离目标的召回 |
| **640 → 512** | 🟡 **中** | max_cls 0.7404→0.7460（无降），但特征图从 80×80 降到 64×64，**小目标分辨率只剩 8×8 像素格**，量化误差 cls 56.1% | 建议只对"大目标"场景评估；小目标场景不建议 |
| **SiLU → ReLU（不重训）** | 🔴 **致命** | 全图最大置信度 0.74→0.027，得分>0.15 的位置 **33.6→0**。**模型输出为空** | **不重训/不微调就不要用**。若必须用，只能走"重训 → 剪枝 → 蒸馏"路线，且要重新标定 conf 阈值 |
| **per-tensor 量化** | 🟡 **中** | cls 张量量化误差 64.4%（per-channel 为 38.9%），**性能上只差 0.8%** | 精度敏感就改回 `quantized_method='channel'`，性能几乎不变 |
| **换基准模型（COCO yolov8n）** | 🔴 **高** | 本次全部结论是在 **yolov8n / 80 类** 上测的，**不是生产在用的 `ebike_int8_rk2332.rknn`**（仓库里没有它的 ONNX 源） | 生产模型只有 2 个输出、无 DFL 调试残留，**绝对数值不可直接外推**；但"SiLU 融合算子更贵"和"分辨率按平方缩放"这两条结构结论是可迁移的 |

---

## 5. 推荐方案

### 5.1 立即落地（本轮）

**采用 C1（SiLU + 576×576）**
- 单帧纯推理 **24.580 ms → 20.134 ms（−18.1%）**，单核 FPS **40.68 → 49.67（+22.1%）**
- 检测置信度 **基本无损**（max_cls 0.7404→0.7235，候选位置数 33.6→34.2）
- 改动面极小：只改 ONNX 输入形状 + 清空输出形状，**权重和图结构一个字没动**
- 交付物已就绪：`model_opt/models/C1_silu_576.rknn`（4.08 MB）

### 5.2 需立项（收益更大，但要付精度代价）

**若允许微调/重训 → 走 SiLU→ReLU 路线**
- 额外 **−27.5%**（C1 20.134 → C2 14.595 ms），叠加后总降幅 **−40.6% ~ −42.5%**
- 机理明确：NPU 侧融合算子 `ConvExSwish`（含 Sigmoid）→ `ConvRelu`（纯比较），
  且 6 个 Add 一并融进 `ConvReluAdd`，算子数 108→102
- 代价：必须重训 + 重新标定 conf 阈值 + 全量精度回归

**生产模型本体也要照着做一遍**
- 本次实验基于仓库里唯一有 ONNX 源的 YOLOv8（yolov8n）。
- 生产的 `ebike_int8_rk2332.rknn` **没有 ONNX 源**（`models/` 只有编译好的 .rknn），
  要对它做同样的改造，**必须先让算法组补出 ONNX**。
- 好消息：生产的 DFL 解码头占 NPU 时间 **39.8%~49.6%**（见 `audit/performance_audit_report.md` §2.3），
  这部分对分辨率不敏感、但对激活敏感，**SiLU→ReLU 在生产模型上的收益可能比 yolov8n 更大**。

### 5.3 不建议

- **单独上 512（不带 ReLU）**：算力口径只比 576 再省 19.5%，但小目标特征图只剩 64×64，
  风险/收益不划算。等 576 的业务回归结果出来再决定。
- **为了"per-tensor"这个指标牺牲精度**：它对性能只值 0.8%，对 cls 量化误差值 25 个百分点。

## 7. 方法学备注（给复现者）

1. **`input_size_list` 在本 toolkit 2.3.2 上对 YOLOv8 无效**（静默忽略）——必须改 ONNX 形状。
2. **改分辨率必须同时清空 ONNX 输出的 shape dim**，否则形状自相矛盾，模型转得出来但检测框全乱。
3. **`/sys/class/devfreq/fdab0000.npu/load` 在本板恒为 100%**，判断 NPU 空闲要用
   `/sys/kernel/debug/rknpu/load` 的逐核百分比。
4. **跑 A/B 前要停的不只是 `rk-gate`**：`rk-pipeline`（崩溃复现器，在 auto-restart 循环里）也会抢 NPU。
5. **多轮轮转比一轮到底更抗污染**：单点测量一旦碰上别的会话抢核就会整组失真
   （本次第一版就踩了：C1 测出 49.8 ms，比 640 的 A0 还慢）。
6. **每轮采样逐核负载做自证**：本测试只用 Core0，Core1/Core2 上出现 >10% 即判定该轮被污染。
7. **`rknn_set_io_mem` 的 attr 必须整体拷贝 `RKNN_QUERY_INPUT_ATTR` 的结果**再改 type/fmt，
   不能 memset 清零 —— 那样 `set_io_mem` 会返回 −1（踩过）。
8. **本报告全部数字来自板端实测**，5 组模型除"激活函数"和"输入分辨率"外，
   量化参数、校准集、Toolkit 版本、优化等级、测试程序、测试时长、核掩码全部一致。
